## Introduction & Architecture

### What is Cloud Composer?

Cloud Composer is Google Cloud's **managed Apache Airflow service**. It abstracts away infrastructure management while providing:

- **Workflow Orchestration**: DAG-based task scheduling
- **Monitoring & Alerting**: Built-in Airflow UI with GCP integration
- **Scalability**: Automatic worker scaling for large DAGs
- **Security**: VPC Service Controls, encryption, IAM

### Historical Context

**Apache Airflow** (started by Airbnb in 2014):
- Initially built to orchestrate Airbnb's data pipelines
- Open-source → adopted by enterprises globally
- Defines workflows as **Directed Acyclic Graphs (DAGs)**
- Declarative: Workflows are code, versionable in Git

**Google Cloud Composer** (launched 2017):
- Airflow managed on GCP
- Auto-scaling, monitoring, updates
- Deep GCP service integration

## Core Components & Concepts

### 1. **DAG (Directed Acyclic Graph)**

A DAG represents a workflow as a directed graph with no cycles.

```python
from airflow import DAG
from airflow.utils.dates import days_ago
from datetime import datetime, timedelta

# DAG definition: blueprint for workflow
default_args = {
    'owner': 'data-engineering',
    'start_date': days_ago(1),
    'retries': 3,
    'retry_delay': timedelta(minutes=5),
    'email_on_failure': True,
    'email': ['alert@company.com']
}

dag = DAG(
    dag_id='daily_etl_pipeline',
    default_args=default_args,
    description='Daily ETL for raw data processing',
    schedule_interval='0 2 * * *',  # 2 AM daily (UTC)
    catchup=False,
    tags=['production', 'etl', 'daily']
)

# DAG Properties:
# dag_id: Unique identifier
# schedule_interval: Cron expression for triggering
# start_date: First execution date
# catchup: Whether to backfill past runs
# default_args: Applied to all tasks unless overridden
```

**Why DAG (not just a list)?**
- Defines **task dependencies** (order matters)
- Enables **parallel execution** (independent tasks run together)
- Makes **failure handling** explicit (which tasks to retry)
- **Visualizes workflow** (DAG graph shows dependencies)

### 2. **Tasks**

A Task is a unit of work in a DAG.

```python
from airflow.operators.gcp_bigquery import BigQueryInsertJobOperator
from airflow.operators.gcp_dataflow import DataflowCreatePythonJobOperator
from airflow.operators.python import PythonOperator
from airflow.operators.gcs import GCSListObjectsOperator
from airflow.operators.dummy import DummyOperator
from airflow.models import Variable
import time

# Task 1: Dummy task (no-op, used for branching)
start = DummyOperator(
    task_id='start',
    dag=dag
)

# Task 2: GCS operation
check_file = GCSListObjectsOperator(
    task_id='check_for_input_file',
    bucket='my-bucket',
    prefix='input/raw_data/',
    dag=dag
)

# Task 3: Python function
def validate_data(**context):
    """Custom Python logic"""
    ti = context['task_instance']
    
    # Get data from XCom (inter-task communication)
    files = ti.xcom_pull(
        task_ids='check_for_input_file'
    )
    
    if not files:
        raise ValueError("No input files found!")
    
    print(f"Validating {len(files)} files")
    time.sleep(5)  # Simulate processing
    
    # Push result to XCom for downstream tasks
    ti.xcom_push(
        key='validated_count',
        value=len(files)
    )

validate = PythonOperator(
    task_id='validate_data',
    python_callable=validate_data,
    provide_context=True,
    dag=dag
)

# Task 4: BigQuery operation
run_bq_query = BigQueryInsertJobOperator(
    task_id='load_to_bigquery',
    configuration={
        'query': {
            'query': '''
                INSERT INTO `my-project.analytics_prod.daily_metrics`
                SELECT 
                  DATE(created_at) AS metric_date,
                  COUNT(*) AS event_count
                FROM `my-project.raw_prod.events`
                WHERE DATE(created_at) = CURRENT_DATE()
                GROUP BY metric_date
            ''',
            'useLegacySql': False,
            'useQueryCache': False,
        }
    },
    dag=dag
)

# Define task dependencies
start >> check_file >> validate >> run_bq_query
# Equivalent to:
# check_file.set_upstream(start)
# validate.set_upstream(check_file)
# run_bq_query.set_upstream(validate)
```

**Task States**:
```
SCHEDULED → QUEUED → RUNNING → SUCCESS
                   ↘ FAILED (with retries)
                   ↘ SKIPPED (conditional execution)
                   ↘ UPSTREAM_FAILED
                   ↘ UPSTREAM_SKIPPED
```

### 3. **Task Dependencies**

Explicit dependency management ensures tasks execute in correct order.

```python
# Linear dependency
task1 >> task2 >> task3 >> task4

# Branching
task1 >> [task2, task3] >> task4
# task2 and task3 run in parallel after task1

# Complex DAG
task1 >> [task2, task3]
task2 >> task5
task3 >> task5
task5 >> task6

# Visualized:
#   task1
#   /   \
# task2 task3
#   \   /
#   task5
#   |
#   task6
```

**Execution Flow**:
1. Scheduler parses DAG every 5 minutes
2. Identifies which tasks are "ready" (all dependencies met)
3. Queues ready tasks to Celery workers
4. Workers execute tasks in parallel
5. Upon completion, downstream tasks become ready

### 4. **XCom (Cross-Communication)**

Inter-task communication mechanism for passing data.

```python
# Upstream task pushes data
def generate_partition_date(**context):
    ti = context['task_instance']
    partition_date = '2024-01-15'
    
    # Push to XCom
    ti.xcom_push(
        key='partition_date',
        value=partition_date
    )

task_push = PythonOperator(
    task_id='generate_date',
    python_callable=generate_partition_date,
    provide_context=True,
    dag=dag
)

# Downstream task pulls data
def process_partition(**context):
    ti = context['task_instance']
    
    # Pull from XCom
    partition_date = ti.xcom_pull(
        task_ids='generate_date',
        key='partition_date'
    )
    
    print(f"Processing partition: {partition_date}")

task_pull = PythonOperator(
    task_id='process_data',
    python_callable=process_partition,
    provide_context=True,
    dag=dag
)

task_push >> task_pull
```

**XCom Limitations**:
- Default size limit: 64 KB (can be increased)
- Not suitable for large datasets (use GCS/BigQuery instead)
- Better for: metadata, configuration, flags

### 5. **Execution Context (context dictionary)**

Passed to every PythonOperator task, contains runtime information.

```python
def example_task(**context):
    # Airflow runtime information
    dag_run = context['dag_run']
    task_instance = context['task_instance']
    execution_date = context['execution_date']
    
    # Task information
    task_id = task_instance.task_id
    dag_id = task_instance.dag_id
    try_number = task_instance.try_number  # Retry count
    
    # Execution timing
    start_date = task_instance.start_date
    
    # Next execution (for backfill logic)
    next_execution_date = dag_run.next_execution_date
    
    # Access variables
    from airflow.models import Variable
    api_key = Variable.get('api_key')
    
    # Push/pull XCom
    task_instance.xcom_push(key='result', value=42)
    upstream_value = task_instance.xcom_pull(
        task_ids='upstream_task',
        key='data'
    )
```

### 2. **Scheduling Patterns**

Cloud Composer supports cron expressions and Airflow presets.

```python
from airflow import DAG

dag_patterns = {
    # Presets
    '@hourly': '0 * * * *',          # Every hour
    '@daily': '0 0 * * *',            # Midnight UTC
    '@weekly': '0 0 * * 0',           # Sunday midnight
    '@monthly': '0 0 1 * *',          # First of month
    '@yearly': '0 0 1 1 *',           # Jan 1
    
    # Custom cron (minute hour day month weekday)
    '0 2 * * *': 'Daily at 2 AM UTC',
    '*/15 * * * *': 'Every 15 minutes',
    '0 2,14 * * *': 'Twice daily (2 AM & 2 PM)',
    '0 9 MON-FRI': 'Weekdays at 9 AM',

```

### 3. **Error Handling & Retries**

```python
from airflow.operators.python import PythonOperator
from airflow.exceptions import AirflowException
from datetime import timedelta

default_args = {
    'retries': 3,  # Retry 3 times
    'retry_delay': timedelta(minutes=5),  # Wait 5 min between retries
    'execution_timeout': timedelta(hours=2),  # Kill task if >2 hrs
    'pool': 'default_pool',  # Limit concurrent task execution
    'pool_slots': 2  # This task uses 2 pool slots
}

def flaky_task():
    """Task that might fail"""
    import random
    if random.random() < 0.5:
        raise AirflowException("Random failure!")
    print("Success!")

task = PythonOperator(
    task_id='flaky_task',
    python_callable=flaky_task,
    dag=dag,
    # Override default_args for this task
    retries=5,
    retry_delay=timedelta(minutes=2)
)
```

### 4. **Conditional Execution**

```python
from airflow.operators.python import BranchPythonOperator

def decide_path(**context):
    """Decide which path to take"""
    partition_date = context['execution_date'].strftime('%Y-%m-%d')
    
    # Return task_id to execute
    if '01-01' in partition_date:  # New year processing
        return 'process_new_year'
    else:
        return 'process_regular'

branch_task = BranchPythonOperator(
    task_id='decide_branch',
    python_callable=decide_path,
    provide_context=True,
    dag=dag
)

process_new_year = PythonOperator(
    task_id='process_new_year',
    python_callable=lambda: print("New year processing"),
    dag=dag
)

process_regular = PythonOperator(
    task_id='process_regular',
    python_callable=lambda: print("Regular processing"),
    dag=dag
)

branch_task >> [process_new_year, process_regular]
```

### 3. **SLA & Alerting**

```python
from airflow.models import DAG
from datetime import timedelta

dag = DAG(
    'sla_example_dag',
    default_args={
        'owner': 'data-eng',
        'start_date': days_ago(1),
        # SLA: Task must complete within this time
        'sla': timedelta(hours=1)
    },
    schedule_interval='@daily',
    # DAG SLA: All tasks must complete by this time
    dagrun_timeout=timedelta(hours=3),
    tags=['sla', 'monitoring']
)

def on_sla_miss(dag, task_list, blocking_task_list, slas, blocking_tis):
    """Called when SLA is missed"""
    from airflow.utils.email import send_email
    
    email_msg = f"""
    SLA missed for DAG: {dag.dag_id}
    Tasks: {[t.task_id for t in task_list]}
    """
    
    send_email(
        to=['alert@company.com'],
        subject=f"SLA miss: {dag.dag_id}",
        html_content=email_msg
    )

dag.sla_miss_callback = on_sla_miss

task1 = PythonOperator(
    task_id='task_with_sla',
    python_callable=lambda: time.sleep(30),
    sla=timedelta(minutes=1),  # Task-level SLA
    dag=dag
)
```

## Execution Models & Scheduling

### 1. **Scheduler Behavior**

```
DAG Definition → Scheduler Parsing → Trigger Run → Task Queuing → Worker Execution

Every scheduler interval (typically 5 minutes):
1. Parse all DAGs from dags/ folder
2. Identify DAG runs due to execute
3. Create DAG run instances
4. Queue "ready" tasks (dependencies met)
5. Workers execute tasks from queue

Execution Date vs. Schedule Date:
- execution_date: Logical date DAG represents
- run_date: When DAG actually triggered
- schedule_interval: Cron for when to trigger

Example:
- Daily DAG at 2 AM UTC
- execution_date: 2024-01-15 (represents day 1/15)
- run_date: 2024-01-16 02:00:00 (triggered next morning)
```

### 2. **Backfilling**

Processing historical data for a date range.

```python
# CLI: backfill DAG for date range
# gcloud composer environments run my-env -- \
#   dags backfill \
#   --dag-id daily_etl_pipeline \
#   --start-date 2024-01-01 \
#   --end-date 2024-01-31

# DAG with catchup enabled
dag = DAG(
    'daily_etl_pipeline',
    start_date=datetime(2024, 1, 1),
    schedule_interval='@daily',
    catchup=True,  # Backfill missing runs
    max_active_runs=3,  # Limit concurrent backfills
    default_args=default_args
)

# When enabled: If DAG has 30 days of missing runs,
# Airflow automatically creates and executes 30 DAG runs
# (respecting max_active_runs concurrency limit)
```

### 3. **Dynamic DAGs**

Generate tasks programmatically.

```python
from airflow import DAG
from airflow.operators.python import PythonOperator
from datetime import datetime

dag = DAG(
    'dynamic_dag',
    start_date=datetime(2024, 1, 1),
    schedule_interval='@daily'
)

# Generate 10 tasks dynamically
tasks = []
for i in range(10):
    task = PythonOperator(
        task_id=f'task_{i}',
        python_callable=lambda x=i: print(f"Executing task {x}"),
        dag=dag
    )
    tasks.append(task)

# Set dependencies dynamically
for i in range(len(tasks)-1):
    tasks[i] >> tasks[i+1]
```

## Interview Questions

### Q1: "Explain Cloud Composer architecture and why separation between Scheduler and Workers matters."

**Expected Answer**:
1. **Scheduler**: Parses DAGs, identifies ready tasks, queues them
   - Single master node
   - Runs DAG definitions every ~5 minutes
   - Doesn't execute tasks (low resource)
2. **Workers**: Execute queued tasks
   - Multiple worker nodes
   - Auto-scale based on queue depth
   - Isolated from scheduler failure
3. **Why separate?**:
   - Scheduler failure doesn't stop running tasks
   - Workers scale independently (handle task spikes)
   - Scheduler stays responsive (not blocked by long-running tasks)

### Q2: "How do you pass data between tasks without overloading XCom?"

**Answer**:
1. **XCom for metadata**: Task IDs, file paths, flags
2. **GCS for large data**: Write to GCS, pass path via XCom
3. **BigQuery for analytics**: Write results to table, pass table path
4. **Cloud Pub/Sub**: For event-driven data passing

### Q3: "Design a data pipeline in Cloud Composer for 50 daily sources."

**Answer**:
- Create DAG with 50 parallel ingestion tasks
- Each task handles one source (API, DB, file)
- Fan-in: Wait for all sources (sensor or dynamic wait)
- Validation phase: Check data quality
- Transformation: PySpark/Dataflow jobs
- Load: BigQuery insert
- Monitoring: SLA, alerting, logging
