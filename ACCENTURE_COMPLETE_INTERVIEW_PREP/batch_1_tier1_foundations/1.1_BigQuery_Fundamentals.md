## Introduction & Historical Context

BigQuery is Google Cloud's **fully managed, serverless data warehouse** launched in 2010. It represents a paradigm shift from traditional OLAP systems:

### Why BigQuery Matters

**Traditional Data Warehouse Problems:**
- MPP (Massively Parallel Processing) databases require capacity planning
- Difficult to scale from GB to TB to PB without re-architecture
- High operational overhead: indexing, partitioning, tuning
- Expensive upfront infrastructure investment

**BigQuery's Solution:**
- **Separation of Compute & Storage**: Query engine scales independently from data storage
- **Columnar Storage Format**: Optimized for analytical queries (read heavy, not write heavy)
- **In-situ Analytics**: Query data directly in GCS without ETL
- **Pay-per-query Model**: Only pay for data scanned, not reserved capacity

### Key Statistics
- Analyzes **100 petabytes per day** across Google's ecosystem
- Processes **10+ million queries per day** globally
- Used by 90%+ of Fortune 100 companies
- Average query response time: **sub-second to seconds** for TB-scale datasets

### Key Components Explained

#### 1. **Dremel Engine (Query Execution)**
- Google's internal query engine (published in VLDB 2010 paper)
- **Columnar Execution**: Processes data column-by-column, not row-by-row
  - Reason: Analytical queries typically access 5-10% of columns
  - Row-based engines would scan unnecessary data
- **Tree-based Aggregation**: Uses hierarchical shuffle-and-reduce
  - Enables **sub-second responses** on 100+ PB datasets
- **Query Compilation Pipeline**:
  ```
  SQL Query 
    ↓ (Lexical Analysis)
  Tokens
    ↓ (Syntax Analysis)
  Abstract Syntax Tree (AST)
    ↓ (Semantic Analysis)
  Logical Query Plan
    ↓ (Cost-based Optimization)
  Physical Query Plan (with execution details)
    ↓ (Code Generation)
  Machine Code for Dremel Execution
  ```

#### 2. **Colossus (Distributed Storage)**
- Google's next-generation distributed file system (successor to GFS)
- **Columnar Storage Format**: Data stored column-by-column, not row-by-row
  - Example: Table with [ID, Name, Age, Salary]
    - Row-based: [1, "Alice", 30, 50000], [2, "Bob", 25, 45000]
    - Column-based: [1, 2, ...], ["Alice", "Bob", ...], [30, 25, ...], [50000, 45000, ...]
  - **Compression Benefits**: Columns with same type compress better (e.g., integers)
  - Typical compression ratios: 5-10x for text, 2-3x for numbers
- **Replication**: Data replicated 3x across Google's infrastructure for durability
- **Regional Distribution**: Data stays within region for compliance

#### 3. **Metadata Service**
- Maintains schema, partitioning info, clustering info, access control
- **Cached locally** for fast lookups
- Tracks table lineage and versioning

## Core Concepts

### 1. **Datasets**
A logical container for tables and views within a project.

```sql
-- Create dataset
CREATE SCHEMA IF NOT EXISTS my_project.analytics_prod
  OPTIONS(
    description = "Production analytics dataset",
    location = "US",
    default_table_expiration_ms = 7776000000  -- 90 days
  );

-- Set access control at dataset level
GRANT roles/bigquery.dataEditor ON SCHEMA my_project.analytics_prod
TO user:analyst@company.com;
```

**Interview Context**: Datasets are your **isolation boundaries**. You'd typically have:
- `raw`: Raw ingestion layer
- `staging`: Transformation layer
- `analytics`: Public consumption layer
- `ml`: ML feature store

### 2. **Tables**
Three types: **Standard Tables**, **Snapshots**, **Clones**

#### Standard Tables
```sql
CREATE OR REPLACE TABLE my_project.analytics_prod.customers (
  customer_id INT64 NOT NULL,
  name STRING,
  email STRING,
  signup_date DATE,
  lifetime_value NUMERIC(12, 2),
  metadata JSON,
  created_at TIMESTAMP NOT NULL,
  updated_at TIMESTAMP NOT NULL
)
PARTITION BY DATE(created_at)
CLUSTER BY customer_id, signup_date
OPTIONS(
  description = "Customer master data",
  require_partition_filter = true,
  kms_key_name = "projects/my-project/locations/US/keyRings/my-key-ring/cryptoKeys/my-key"
);
```

**Why this structure?**
- `PARTITION BY DATE(created_at)`: Queries filtered by date scan only relevant partitions
  - If you query `WHERE created_at >= '2024-01-01'`, BigQuery skips older partitions entirely
  - Reduces data scanned → Reduces cost
- `CLUSTER BY customer_id, signup_date`: Within each partition, data physically sorted by these columns
  - Improves cache hit rates for repeated queries
  - Better for point lookups and range scans
- `require_partition_filter = true`: Enforces partition filter in queries
  - Prevents accidental full-table scans

#### Table Snapshots & Clones (BigQuery+ feature)
```sql
-- Create point-in-time snapshot
CREATE SNAPSHOT TABLE my_project.analytics_prod.customers_snapshot_2024_01_01
CLONE my_project.analytics_prod.customers
FOR SYSTEM_TIME AS OF TIMESTAMP_SUB(CURRENT_TIMESTAMP(), INTERVAL 30 DAY);

-- Clone for testing
CREATE OR REPLACE TABLE my_project.analytics_dev.customers
CLONE my_project.analytics_prod.customers;
```

**Use Cases**:
- **Time travel**: Query data as it existed 30 days ago
- **Safe testing**: Clone to dev for testing without affecting production
- **Audit trails**: Maintain snapshots for regulatory compliance

### 3. **Views**
Two types: **Logical Views** and **Materialized Views**

#### Logical Views
```sql
CREATE OR REPLACE VIEW my_project.analytics_prod.vw_high_value_customers AS
SELECT 
  customer_id,
  name,
  lifetime_value,
  CASE 
    WHEN lifetime_value > 100000 THEN 'Platinum'
    WHEN lifetime_value > 50000 THEN 'Gold'
    ELSE 'Silver'
  END AS tier
FROM my_project.analytics_prod.customers
WHERE lifetime_value > 10000;
```

**Characteristics**:
- **Virtual**: No physical storage
- **Query re-writes**: When queried, BigQuery expands the view definition
- **Up-to-date**: Always reflects current data
- **Performance**: Can be slower (no caching)

#### Materialized Views
```sql
CREATE MATERIALIZED VIEW my_project.analytics_prod.mv_daily_sales AS
SELECT 
  DATE(order_date) AS order_date,
  product_category,
  SUM(sale_amount) AS total_sales,
  COUNT(DISTINCT customer_id) AS unique_customers,
  COUNT(*) AS order_count
FROM my_project.raw_prod.orders
WHERE order_date >= DATE_SUB(CURRENT_DATE(), INTERVAL 365 DAY)
GROUP BY order_date, product_category;
```

**Characteristics**:
- **Physical**: Data physically stored, updated periodically
- **Fast queries**: Queries run against pre-aggregated data
- **Stale data**: Updated on defined schedule (can be configured)
- **Automatic rewrite**: BigQuery rewrites queries to use materialized view when possible

**When to use?**:
- **Logical views**: For simple transformations, security filtering (row-level access)
- **Materialized views**: For expensive aggregations queried repeatedly (OLAP cubes)

### 4. **External Tables**
Query data in GCS without loading into BigQuery.

```sql
CREATE OR REPLACE EXTERNAL TABLE my_project.raw_prod.events_external
OPTIONS (
  format = 'PARQUET',
  uris = ['gs://my-bucket/events/2024/01/*.parquet'],
  require_partition_filter = false
);

-- Query external table (scans GCS directly)
SELECT 
  event_id,
  user_id,
  event_type,
  event_timestamp
FROM my_project.raw_prod.events_external
WHERE DATE(event_timestamp) = '2024-01-15';
```

**When to use?**:
- **Data too large to load**: Petabyte-scale data exploration
- **Cost-sensitive queries**: Don't pay BigQuery storage, only query cost
- **Data governance**: Keep sensitive data in GCS, control access via external table permissions
- **Real-time data**: Query freshly arrived files without ETL delay

**Performance caveat**: External tables are **slower** (10-100x) than native tables due to GCS latency. Use for exploration, not high-frequency queries.

## Data Models & Schema Design

### 1. **Denormalization vs. Normalization**

#### Traditional Relational (Normalized)
```sql
-- NORMALIZED: Multiple tables with JOINs
CREATE TABLE customers (
  customer_id INT64 PRIMARY KEY,
  name STRING,
  country_id INT64
);

CREATE TABLE countries (
  country_id INT64 PRIMARY KEY,
  country_name STRING,
  region_id INT64
);

CREATE TABLE regions (
  region_id INT64 PRIMARY KEY,
  region_name STRING
);

-- Query requires 2 JOINs
SELECT c.customer_id, c.name, cnt.country_name, r.region_name
FROM customers c
JOIN countries cnt ON c.country_id = cnt.country_id
JOIN regions r ON cnt.region_id = r.region_id;
```

**Problems in BigQuery context**:
- JOINs require shuffle operations (expensive)
- Multiple table scans
- Slower for analytical queries

#### BigQuery Style (Denormalized)
```sql
-- DENORMALIZED: All data in one table
CREATE TABLE customers_denorm (
  customer_id INT64 NOT NULL,
  name STRING,
  country_name STRING,
  region_name STRING
)
PARTITION BY customer_id
CLUSTER BY region_name;

-- Query is simple, fast, no JOINs
SELECT 
  customer_id,
  name,
  country_name,
  region_name
FROM customers_denorm;
```

**Why?**:
- Columnar storage is cheap → Storage is not the bottleneck
- Query speed is the bottleneck → Denormalize to eliminate JOINs
- BigQuery's compute is massively parallel → Can handle wide tables efficiently

**Interview Answer**:
> "In OLTP (Online Transaction Processing), we normalize to reduce storage and update anomalies. In OLAP (Online Analytical Processing) like BigQuery, we denormalize because storage is cheap and retrieval is expensive. A single table scan is faster than multiple JOINs."

### 2. **Nested & Repeated Fields**

BigQuery supports **STRUCT** (nested objects) and **ARRAY** (repeated fields) natively.

```sql
CREATE TABLE events (
  event_id STRING NOT NULL,
  user STRUCT<
    user_id STRING,
    user_properties STRUCT<
      name STRING,
      age INT64,
      tags ARRAY<STRING>
    >
  >,
  event_details ARRAY<STRUCT<
    key STRING,
    value STRING
  >>,
  event_timestamp TIMESTAMP NOT NULL
)
PARTITION BY DATE(event_timestamp)
CLUSTER BY user.user_id;

-- Query nested fields
SELECT 
  event_id,
  user.user_id,
  user.user_properties.name,
  ARRAY_LENGTH(user.user_properties.tags) AS tag_count,
  event_details
FROM events
WHERE DATE(event_timestamp) = CURRENT_DATE()
AND user.user_properties.age > 25;

-- Unnest repeated fields
SELECT 
  event_id,
  user.user_id,
  detail.key,
  detail.value
FROM events,
UNNEST(event_details) AS detail
WHERE DATE(event_timestamp) = CURRENT_DATE();
```

**Advantages**:
- **Denormalization in structure**: Keep related data together
- **Preserves schema intent**: Represent one-to-many relationships explicitly
- **Query efficiency**: No JOINs required for nested data
- **Storage efficiency**: Compression works better with grouped data

## Pricing Model & Cost Implications

### 1. **Analysis Pricing (Query Cost)**

BigQuery charges **$6.25 per TB of data scanned** (as of 2024) in on-demand mode.

```
Query Cost = (Total Bytes Scanned) / (1 TB) * $6.25
```

**Key Rules**:
- **Minimum per query**: $0 (queries returning cached results don't incur cost)
- **Cached results**: If same query runs within 24h, no cost
- **Column pruning**: Only columns referenced in SELECT are scanned
- **Partition pruning**: Only partitions matching WHERE filters are scanned
- **Clustering pruning**: Within partitions, only blocks with matching cluster keys are scanned

#### Example Cost Calculation

Table: `transactions` with 100 GB of data
```sql
-- Query 1: Full table scan
SELECT * FROM transactions;
-- Cost: 100 GB = 0.1 TB * $6.25 = $0.625

-- Query 2: Single column with partition filter
SELECT customer_id 
FROM transactions 
WHERE DATE(created_at) = '2024-01-15';
-- Cost: 5 GB (only 1 day's data, 1 column) = 0.005 TB * $6.25 = $0.03125

-- Query 3: Clustered lookup
SELECT * FROM transactions 
WHERE DATE(created_at) = '2024-01-15' 
AND customer_id = '12345';
-- Cost: 1 GB (partition + cluster pruning) = 0.001 TB * $6.25 = $0.00625
```

### 2. **Storage Pricing**

- **Active storage** (used within 90 days): $0.02 per GB/month
- **Long-term storage** (not modified >90 days): $0.01 per GB/month

```
Example: 10 TB table at active rates
Cost/month = 10 * 1024 GB * $0.02 = $204.80/month
```

### 3. **Cost Optimization Strategies**

**Strategy 1: Partitioning**
```sql
-- BAD: Full table scan
SELECT COUNT(*) FROM events WHERE DATE(event_date) = '2024-01-15';
-- Scans entire table, costs: 100 GB * $6.25 / 1024 = $0.61

-- GOOD: Partitioned by date
SELECT COUNT(*) FROM events WHERE DATE(event_date) = '2024-01-15';
-- Scans 1 day of data, costs: 5 GB * $6.25 / 1024 = $0.031 (20x cheaper!)
```

**Strategy 2: Clustering**
```sql
-- Without clustering: Full scan of daily partition
SELECT * FROM events 
WHERE DATE(event_date) = '2024-01-15' 
AND user_id = '12345';
-- Scans 5 GB = $0.031

-- With clustering by user_id: Scan only user's blocks
SELECT * FROM events 
WHERE DATE(event_date) = '2024-01-15' 
AND user_id = '12345';
-- Scans 100 MB = $0.00006 (500x cheaper!)
```

**Strategy 3: Column Projection**
```sql
-- BAD: Select *
SELECT * FROM users;  -- 50 GB

-- GOOD: Select only needed columns
SELECT user_id, name, email FROM users;  -- 5 GB (10x cheaper!)
```

**Strategy 4: Query Caching**
```sql
-- Run same query twice
SELECT COUNT(*) FROM events;  -- First time: scans data, costs $0.61
SELECT COUNT(*) FROM events;  -- Second time: cached, costs $0 (1 hour cache)
```

## Security & Access Control

### 1. **Identity & Access Management (IAM)**

BigQuery uses Google Cloud's hierarchical IAM model:

```
Organization
  ↓
Project (e.g., my-company-prod)
  ├─ Dataset (e.g., analytics_prod)
  │   ├─ Table (e.g., customers)
  │   └─ Table (e.g., orders)
  └─ Dataset (e.g., ml_models)
      └─ Table (e.g., features)
```

**Role-Based Access Control (RBAC)**:
```sql
-- Grant analyst access to view all tables in dataset
GRANT roles/bigquery.dataViewer ON SCHEMA my_project.analytics_prod 
TO user:analyst@company.com;

-- Grant engineer access to create and modify tables
GRANT roles/bigquery.dataEditor ON SCHEMA my_project.analytics_prod 
TO user:engineer@company.com;

-- Grant admin access
GRANT roles/bigquery.admin ON PROJECT my_project 
TO user:admin@company.com;
```

**Common Roles**:
- `bigquery.viewer`: Read-only access to data
- `bigquery.dataViewer`: Query data, read table metadata
- `bigquery.dataEditor`: Create/modify tables, run queries
- `bigquery.admin`: Full control including dataset deletion

### 2. **Row-Level Security (RLS)**

BigQuery supports row-level access control via **authorized views**:

```sql
-- Base table (not directly accessible)
CREATE TABLE my_project.raw_prod.employees_internal (
  employee_id INT64,
  name STRING,
  salary INT64,
  department STRING,
  manager_id INT64
);

-- Authorized view (controlled access)
CREATE OR REPLACE VIEW my_project.analytics_prod.vw_employees_limited
AS
SELECT 
  employee_id,
  name,
  department
  -- Intentionally exclude salary
FROM my_project.raw_prod.employees_internal
WHERE department = (
  -- Manager can only see their own department
  SELECT department FROM my_project.raw_prod.employees_internal 
  WHERE employee_id = SESSION_USER()
);
```

**Interview Context**: 
> "To implement RLS, you'd create a view that filters rows based on the querying user, then grant access to the view (not the table). BigQuery evaluates the view query using the logged-in user's context."

### 3. **Encryption**

**Encryption at Rest**:
```sql
CREATE TABLE my_project.analytics_prod.sensitive_data (
  customer_id INT64,
  ssn STRING,
  credit_card STRING
)
OPTIONS(
  kms_key_name = 'projects/my-project/locations/US/keyRings/my-ring/cryptoKeys/my-key'
);
```

BigQuery encrypts all data at rest using **Google-managed keys** by default. For compliance, use **Customer-managed keys (CMEK)** via Cloud KMS.

**Encryption in Transit**:
- All data in transit between client and BigQuery is encrypted via TLS 1.2+
- All data shuffled between nodes during queries is encrypted

## Common Interview Questions

### Q1: "Explain BigQuery's architecture. Why is it fast?"

**Expected Answer Structure**:
1. **Separation of Compute & Storage**: BigQuery decouples query execution (Dremel) from storage (Colossus). Storage scales independently, compute scales on-demand.
2. **Columnar Storage**: Data stored column-by-column. Queries scan only needed columns. Example: Summing revenue from 1000-column table scans only revenue column.
3. **Tree-based Aggregation**: Dremel uses hierarchical shuffle-reduce. Instead of single reducer, intermediate servers aggregate, enabling sub-second responses on petabyte datasets.
4. **Massive Parallelism**: Each query spreads across thousands of machines. A 1 TB table scan happens on 1000+ machines in parallel.

### Q2: "What's the difference between partitioning and clustering?"

**Partitioning**:
- Divides table into **mutually exclusive segments** (physical separation)
- Example: By `DATE(created_at)`, table splits into one partition per day
- BigQuery **skips entire partitions** if query filters exclude them
- Limited partitions: BigQuery supports ~4000 partitions per table
- Best for: Time-series data, large filtering ranges

**Clustering**:
- Sorts data **within each partition** by specified columns
- Example: Within each day partition, data sorted by `user_id`
- BigQuery **skips blocks** if cluster columns don't match
- No partition limit, supports up to 4 cluster columns
- Best for: Frequent point lookups, range scans

```sql
-- Partitioned by date, clustered by user_id
CREATE TABLE events (
  event_id STRING,
  user_id STRING,
  created_at TIMESTAMP
)
PARTITION BY DATE(created_at)
CLUSTER BY user_id;

-- This query is optimal
SELECT * FROM events 
WHERE DATE(created_at) = '2024-01-15' 
AND user_id = 'user123';
-- Scans: only Jan 15 partition, only blocks for user123
```

### Q3: "How do you optimize BigQuery costs?"

**Answer**:
1. **Partition & Cluster**: Reduces data scanned (e.g., 10x savings)
2. **Column Projection**: Select only needed columns (e.g., 5-10x savings)
3. **Query Caching**: Reuse results from recent queries (free)
4. **Approximate Aggregations**: Use APPROX_QUANTILES instead of EXACT for sketches (faster, cheaper)
5. **Materialized Views**: Pre-aggregate expensive transformations
6. **Slot Reservations**: For predictable workloads, buy annual slots cheaper than on-demand

### Q4: "What happens when you query an external table vs. a native table?"

**External Table**:
- Data stays in GCS
- BigQuery scans files directly from GCS
- **Slower** (10-100x) due to network latency and lack of optimizations
- **Cheaper storage** (pay GCS, not BigQuery storage)
- **Slower cache**: External table metadata cached, but actual data not cached in Colossus

**Native Table**:
- Data stored in Colossus
- Optimized columnar format
- **Faster** (100-1000x) due to local storage and optimizations
- **More expensive storage**

### Q5: "Explain BigQuery's execution model for a JOIN query."

```sql
SELECT 
  c.customer_id,
  c.name,
  o.order_id,
  o.amount
FROM customers c
JOIN orders o ON c.customer_id = o.customer_id
WHERE c.signup_date > '2024-01-01';
```

**Execution Steps**:
1. **Parse & Compile**: SQL parsed, logical plan created
2. **Optimization**: Cost-based optimizer rewrites plan
   - Push date filter to customers table (predicate pushdown)
   - Logical plan: Filter customers → Join with orders
3. **Physical Plan**: Decide execution strategy
   - Small table broadcast join (if customers is small)
   - Shuffle join (if both tables large)
4. **Execution**:
   - Scan filtered customers (10 million rows)
   - Hash partition by customer_id
   - Scan orders, partition by customer_id
   - Shuffle phase: Repartition both tables by customer_id
   - Join phase: Merge-join on each worker
   - Aggregation (if any) via tree-based reduction
5. **Result**: Stream results back to client

## Summary & Key Takeaways

| Concept | Key Point | Interview Hook |
|---------|-----------|-----------------|
| **Architecture** | Dremel (compute) + Colossus (storage) separate | "Why can it scale to petabytes?" |
| **Columnar Storage** | Only scanned columns read from disk | "Why only select needed columns?" |
| **Partitioning** | Divides table into segments; BQ skips partitions | "How to optimize for date filters?" |
| **Clustering** | Sorts within partitions; BQ skips blocks | "What about non-date filters?" |
| **Denormalization** | Store wide tables, avoid JOINs | "Why no normalization?" |
| **Nested Fields** | STRUCT/ARRAY enable semi-denormalization | "How to avoid JOINs?" |
| **Cost Model** | Pay per TB scanned, not capacity | "How to cost-optimize?" |
| **External Tables** | Query GCS without loading | "When to use external tables?" |
