## Query Performance Optimization

### 1. **Query Execution Analysis**

Every BigQuery query generates an **execution plan** showing:
- Data scanned (bytes)
- Bytes shuffled (inter-node communication)
- Execution stages and their duration
- Worker utilization

#### Reading Execution Plans

```
Query Job: bq ls -j -a -n 100 | grep <job_id>

Timeline:
├─ Stage 0: Table scan (customers)
│  └─ 10 GB scanned, 0 MB shuffled, 2.5s elapsed
├─ Stage 1: Filter & projection
│  └─ Input: 50M rows, Output: 5M rows, 1.2s elapsed
├─ Stage 2: Hash aggregation
│  └─ Input: 5M rows, Output: 1K rows (shuffled), 3.1s elapsed
└─ Stage 3: Final aggregation
   └─ Input: 1K rows, Output: 100 rows, 0.3s elapsed

Total: 10 GB scanned, 2 MB shuffled, 7.1s query time
```

**Interpretation**:
- **Shuffle spike**: Large data movement between stages → Consider partitioning
- **Long stage**: Specific stage taking time → Optimize that operation
- **High worker count**: Parallelism being utilized effectively

### 2. **Predicate Pushdown**

Query optimizer pushes filters as early as possible in execution plan.

#### Good Example (Predicate Pushdown Works)
```sql
SELECT 
  user_id,
  COUNT(*) AS action_count
FROM events
WHERE DATE(event_timestamp) = '2024-01-15'
AND event_type = 'click'
GROUP BY user_id;

-- Execution:
-- Stage 0: Scan events table
--   → BigQuery pushes DATE and event_type filters to storage layer
--   → Only scans 1 day of data, only clicks
--   → 100 GB → 5 GB after filtering
-- Stage 1: Hash aggregation on 5 GB → Count per user
```

#### Bad Example (Predicate Pushdown Fails)
```sql
SELECT 
  user_id,
  COUNT(*) AS action_count,
  MAX(revenue) AS max_revenue
FROM events
WHERE EXTRACT(QUARTER FROM event_timestamp) = 1  -- Q1
AND event_type = 'purchase'
GROUP BY user_id;

-- Execution:
-- Stage 0: Scan events table (full table)
--   → EXTRACT() function cannot be pushed down
--   → BigQuery scans entire table (100 GB)
-- Stage 1: Filter by EXTRACT(QUARTER) = 1
--   → After filtering: 25 GB (Q1 data)
-- Stage 2: Hash aggregation
```

**Optimization**: Use partition-compatible filters
```sql
-- GOOD: Partition filter that BigQuery understands
SELECT 
  user_id,
  COUNT(*) AS action_count
FROM events
WHERE event_timestamp >= '2024-01-01'
AND event_timestamp < '2024-04-01'  -- Q1
AND event_type = 'purchase'
GROUP BY user_id;

-- BigQuery can push these to storage layer
```

### 3. **JOIN Strategies**

BigQuery supports three JOIN implementations:

#### Broadcast Join (Small Table Joins)
```sql
-- Assume: customers (1M rows, 100 MB) vs orders (1B rows, 10 GB)
SELECT 
  c.customer_id,
  c.name,
  COUNT(o.order_id) AS order_count
FROM customers c
LEFT JOIN orders o ON c.customer_id = o.customer_id
GROUP BY c.customer_id, c.name;

-- Execution:
-- 1. Scan & broadcast customers (100 MB) to all workers
-- 2. Scan orders, hash-join locally with broadcasted customers
-- 3. Each worker processes partition of orders
-- Total shuffle: 100 MB (broadcast), not 10 GB
```

**Optimization**: Join order matters when one table is much smaller
```sql
-- GOOD: Join small first
SELECT *
FROM large_table l
JOIN small_table s ON l.id = s.id;

-- BAD: Join large first
SELECT *
FROM small_table s
JOIN large_table l ON s.id = l.id;

-- Both execute same way, but code clarity matters
```

#### Shuffle Join (Both Tables Large)
```sql
-- Both tables large (5 GB each)
SELECT 
  d.department_id,
  d.name,
  SUM(s.salary) AS total_salary
FROM departments d
JOIN salaries s ON d.department_id = s.department_id
GROUP BY d.department_id, d.name;

-- Execution:
-- 1. Hash partition departments by department_id
-- 2. Hash partition salaries by department_id
-- 3. Shuffle: Move partitions to same workers (5 GB + 5 GB)
-- 4. Local join on each worker
-- Total shuffle: 10 GB (both tables)
```

**Optimization**: Filter before join to reduce shuffle size
```sql
-- GOOD: Filter before join (reduce from 5 GB to 1 GB)
SELECT 
  d.department_id,
  d.name,
  SUM(s.salary) AS total_salary
FROM departments d
WHERE d.department_id IN (SELECT DISTINCT department_id FROM salaries WHERE salary > 100000)
JOIN salaries s ON d.department_id = s.department_id
WHERE s.salary > 100000
GROUP BY d.department_id, d.name;

-- Execution:
-- 1. Scan salaries (5 GB), filter salary > 100000 (1 GB), extract departments (100 MB)
-- 2. Scan departments (5 GB), filter by subquery (1 GB)
-- 3. Shuffle: 1 GB + 1 GB = 2 GB (vs. 10 GB unoptimized)
```

#### Correlated Subqueries (Avoid!)
```sql
-- BAD: Correlated subquery (very slow)
SELECT 
  customer_id,
  name,
  (SELECT COUNT(*) FROM orders o WHERE o.customer_id = c.customer_id) AS order_count
FROM customers c;

-- Execution:
-- For each customer, execute subquery → 1M queries for 1M customers
-- Very slow and expensive

-- GOOD: Left join with aggregation
SELECT 
  c.customer_id,
  c.name,
  COUNT(o.order_id) AS order_count
FROM customers c
LEFT JOIN orders o ON c.customer_id = o.customer_id
GROUP BY c.customer_id, c.name;

-- Execution:
-- 1. Single scan of customers
-- 2. Single scan of orders
-- 3. Shuffle join
-- 4. Aggregation
```

### 4. **Window Functions & Analytics**

Window functions are highly optimized in BigQuery. Use them instead of self-joins.

```sql
-- BAD: Self-join to calculate running total
SELECT 
  a.order_id,
  a.order_date,
  a.amount,
  SUM(b.amount) AS running_total
FROM orders a
JOIN orders b ON a.order_date >= b.order_date
GROUP BY a.order_id, a.order_date, a.amount
ORDER BY a.order_date;

-- Execution:
-- 1. Scan orders twice (cartesian join → 1B * 1B rows)
-- 2. Very slow, high shuffle

-- GOOD: Window function
SELECT 
  order_id,
  order_date,
  amount,
  SUM(amount) OVER (
    PARTITION BY MONTH(order_date)
    ORDER BY order_date
    ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW
  ) AS running_total
FROM orders
ORDER BY order_date;

-- Execution:
-- 1. Single table scan
-- 2. Compute window functions over partitions
-- 3. Fast, low shuffle
```

**Advanced Window Functions**:
```sql
SELECT 
  user_id,
  purchase_date,
  amount,
  -- Running total
  SUM(amount) OVER (
    PARTITION BY user_id
    ORDER BY purchase_date
  ) AS cumulative_amount,
  -- Ranking
  ROW_NUMBER() OVER (
    PARTITION BY user_id
    ORDER BY purchase_date DESC
  ) AS most_recent_rank,
  -- Lag/Lead
  LAG(amount) OVER (
    PARTITION BY user_id
    ORDER BY purchase_date
  ) AS previous_purchase_amount,
  LEAD(amount) OVER (
    PARTITION BY user_id
    ORDER BY purchase_date
  ) AS next_purchase_amount,
  -- Percentage rank
  PERCENT_RANK() OVER (
    PARTITION BY user_id
    ORDER BY amount
  ) AS amount_percentile
FROM purchases
ORDER BY user_id, purchase_date;
```

### 5. **APPROX Aggregations**

For large datasets, exact aggregations are expensive. Use APPROX functions for sketches.

```sql
-- Exact aggregations (expensive, scans all data)
SELECT 
  DATE(created_at) AS date,
  COUNT(DISTINCT user_id) AS exact_unique_users,
  APPROX_COUNT_DISTINCT(user_id) AS approx_unique_users
FROM events
GROUP BY DATE(created_at);

-- Example output:
-- date       | exact_unique_users | approx_unique_users | error
-- 2024-01-01 | 1,234,567         | 1,234,823          | 0.02% error

-- Approx results: Within 1-2% error, 10-100x faster
```

**Common APPROX Functions**:
- `APPROX_COUNT_DISTINCT()`: Cardinality estimation
- `APPROX_QUANTILES()`: Percentile estimation without sorting entire dataset
- `APPROX_TOP_COUNT()`: Top-K elements without full aggregation

```sql
-- APPROX_QUANTILES: Find P99 latency without sorting 1B rows
SELECT 
  service_name,
  APPROX_QUANTILES(latency_ms, 100)[OFFSET(99)] AS p99_latency,
  APPROX_QUANTILES(latency_ms, 100)[OFFSET(50)] AS p50_latency,
  APPROX_QUANTILES(latency_ms, 100)[OFFSET(95)] AS p95_latency
FROM request_logs
WHERE DATE(timestamp) = CURRENT_DATE()
GROUP BY service_name;
```

## Storage Optimization

### 1. **Data Format Selection**

BigQuery supports multiple input/output formats. Choice affects storage, speed, and compatibility.

#### Parquet (Recommended)
```python
# Write to GCS as Parquet
job_config = bigquery.LoadJobConfig(source_format=bigquery.SourceFormat.PARQUET)

job = client.load_table_from_uri(
    "gs://my-bucket/data.parquet",
    table_id,
    job_config=job_config
)
job.result()

# Why Parquet?
# - Columnar format (matches BigQuery internals)
# - Compression: 5-10x for analytical data
# - Schema preservation: Type inference
# - Splittable: BigQuery can read in parallel
```

#### CSV (Legacy, Not Recommended)
```python
# CSV requires more specification
job_config = bigquery.LoadJobConfig(
    source_format=bigquery.SourceFormat.CSV,
    skip_leading_rows=1,
    field_delimiter=",",
    allow_jagged_rows=False,
    allow_quoted_newlines=True
)

# Why avoid CSV?
# - Row-oriented (inefficient for analytics)
# - No compression
# - Type inference ambiguous (is "123" int or string?)
# - Large file size (10 GB CSV → 1-2 GB Parquet)
```

#### Avro (Streaming)
```python
# Avro good for streaming ingestion
job_config = bigquery.LoadJobConfig(source_format=bigquery.SourceFormat.AVRO)

# Why Avro?
# - Schema-aware
# - Good for streaming pipelines
# - Compact
# - Language-agnostic
```

### 2. **Compression Strategies**

Different compression algorithms have trade-offs:

| Format | Size Reduction | Speed | Use Case |
|--------|---|---|---|
| **GZIP** | 5-10x | Slow to decompress | Cold data, infrequent access |
| **Snappy** | 2-3x | Fast decompress | Streaming, real-time |
| **Brotli** | 5-8x | Medium | Default for BigQuery |

```python
# Configure compression for export
job_config = bigquery.ExtractJobConfig()
job_config.compression = bigquery.Compression.GZIP  # vs. SNAPPY, DEFLATE
job_config.destination_format = bigquery.DestinationFormat.PARQUET

# For 10 TB table:
# GZIP: 1-2 TB file, slow read
# Snappy: 3-4 TB file, fast read
# Brotli: 1.5-2.5 TB file, medium read
```

### 3. **Table Expiration Policies**

Automatically delete old data to control storage costs.

```sql
-- Expire table partitions after 90 days
CREATE TABLE my_project.staging.raw_events (
  event_id STRING,
  event_timestamp TIMESTAMP,
  ...
)
PARTITION BY DATE(event_timestamp)
OPTIONS(
  partition_expiration_days = 90
);

-- Expire entire table after 30 days
CREATE TEMP TABLE temp_results (
  ...
)
OPTIONS(
  expiration_timestamp = TIMESTAMP_ADD(CURRENT_TIMESTAMP(), INTERVAL 30 DAY)
);

-- Set dataset-level default
ALTER SCHEMA my_project.staging
SET OPTIONS(
  default_table_expiration_ms = 7776000000  -- 90 days
);
```

### 4. **Clustering for Both Query & Storage Optimization**

Clustering provides dual benefits:

```sql
-- Events table: 1 TB, 365 daily partitions
CREATE TABLE events (
  event_id STRING,
  user_id STRING,
  event_type STRING,
  timestamp TIMESTAMP,
  properties JSON
)
PARTITION BY DATE(timestamp)
CLUSTER BY user_id, event_type;

-- Before clustering:
-- Each partition (1 day): 2-3 GB
-- To find all "clicks" by user123 on Jan 15: scan full 2-3 GB

-- After clustering:
-- Each partition sorted by user_id, then event_type
-- To find clicks by user123 on Jan 15: scan 20-50 MB (100x improvement)
```

## Advanced Features: Slots & BI Engine

### 1. **BigQuery Slots (Reserved Capacity)**

For workloads with predictable query volume, slots are cheaper than on-demand.

```
On-Demand:
- $6.25 per TB scanned
- Pay per query
- Example: 100 TB/day = $625/day = $18,750/month

Annual Slots:
- $48,000/year = $4,000/month for 100 slots
- 100 slots = ~100 TB/day capacity
- Commitment-based, not pay-per-query
- Better for: Continuous analytics, dashboards, reporting
```

**Slot Allocation**:
```python
# Create slot reservation
slots_client = bigquery.CapacityAdminClient()

reservation = bigquery.Reservation(
    slot_capacity=100,
    concurrency_limit=None  # Unlimited concurrent queries within capacity
)

created_reservation = slots_client.create_reservation(
    parent="projects/my-project/locations/US",
    reservation=reservation
)

# Assign dataset to slot reservation
dataset_reference = bigquery.DatasetReference("my-project", "analytics_prod")
dataset = bigquery.Dataset(dataset_reference)
dataset.default_repartition_expiration_ms = 7776000000

slots_client.update_dataset(dataset)
```

### 2. **BI Engine (Cached Analytics Engine)**

BI Engine pre-caches aggregations for faster BI tool queries (Looker, Tableau, etc.).

```sql
-- Create materialized view pinned to BI Engine
CREATE MATERIALIZED VIEW my_project.analytics_prod.bi_cache_daily_sales AS
SELECT 
  DATE(order_date) AS order_date,
  product_category,
  region,
  SUM(sale_amount) AS total_sales,
  COUNT(DISTINCT customer_id) AS unique_customers,
  COUNT(*) AS order_count
FROM my_project.raw_prod.orders
WHERE order_date >= DATE_SUB(CURRENT_DATE(), INTERVAL 365 DAY)
GROUP BY order_date, product_category, region;

-- BI Engine automatically caches this aggregation in RAM
-- Queries hitting this materialized view: 100-1000x faster
```

**Cost-Benefit**:
- BI Engine: $0.04 per GB/month (RAM cache)
- 100 GB cached aggregations: $4/month
- Typical BI query time: 5 seconds → 50ms (100x speedup)
- Worth it for: High-frequency BI queries, dashboards with many filters

## Real-World Case Studies

### Case Study 1: Optimizing a Daily 500 GB ETL Pipeline

**Initial State**:
```sql
-- Original query: 2 hours, $31.25 cost daily
INSERT INTO my_project.analytics_prod.daily_metrics
SELECT 
  DATE(transaction_timestamp) AS transaction_date,
  store_id,
  product_category,
  SUM(amount) AS total_sales,
  COUNT(DISTINCT customer_id) AS unique_customers,
  AVG(amount) AS avg_transaction
FROM my_project.raw_prod.transactions  -- 500 GB table, not partitioned
WHERE DATE(transaction_timestamp) = CURRENT_DATE() - 1
GROUP BY transaction_date, store_id, product_category;

-- Full 500 GB scanned every day!
```

**Optimization Steps**:

1. **Add Partitioning**:
```sql
-- Recreate table with partitioning
CREATE OR REPLACE TABLE my_project.raw_prod.transactions (
  transaction_id STRING,
  transaction_timestamp TIMESTAMP,
  store_id INT64,
  product_category STRING,
  amount NUMERIC(12, 2)
)
PARTITION BY DATE(transaction_timestamp)
CLUSTER BY store_id, product_category;

-- Scan reduced: 500 GB → 1-2 GB (1 day of data)
-- Cost reduced: $31.25 → $0.10 (312x!)
-- Time reduced: 2 hours → 5 seconds
```

2. **Add Clustering**:
```sql
-- Already added above
-- For the 1-2 GB daily data, cluster by store_id and product_category
-- When aggregating by store_id and product_category, only scan relevant blocks
-- Time reduced: 5 seconds → 0.5 seconds
```

3. **Use Materialized View for Repeated Queries**:
```sql
CREATE MATERIALIZED VIEW my_project.analytics_prod.mv_daily_metrics AS
SELECT 
  DATE(transaction_timestamp) AS transaction_date,
  store_id,
  product_category,
  SUM(amount) AS total_sales,
  COUNT(DISTINCT customer_id) AS unique_customers,
  AVG(amount) AS avg_transaction
FROM my_project.raw_prod.transactions
WHERE DATE(transaction_timestamp) >= DATE_SUB(CURRENT_DATE(), INTERVAL 365 DAY)
GROUP BY transaction_date, store_id, product_category;

-- Now all downstream queries use this MV instead of raw table
-- No additional scans for repeat queries
```

**Results**:
- **Daily cost**: $31.25 → $0.10 (312x reduction)
- **Monthly savings**: $937.50
- **Query time**: 2 hours → 0.5 seconds (14,400x improvement)
- **Annual savings**: $11,250

### Case Study 2: User Segmentation Query (Billion Rows)

**Problem**: Segment 1 billion users by engagement level. Query timeout after 1 hour.

**Initial Query**:
```sql
-- Times out (cartesian join with self)
WITH user_metrics AS (
  SELECT 
    user_id,
    COUNT(*) AS action_count,
    COUNT(DISTINCT DATE(event_timestamp)) AS active_days
  FROM raw_prod.events
  WHERE DATE(event_timestamp) >= DATE_SUB(CURRENT_DATE(), INTERVAL 90 DAY)
  GROUP BY user_id
)
SELECT 
  u.user_id,
  u.action_count,
  u.active_days,
  CASE 
    WHEN u.action_count > (SELECT PERCENTILE_CONT(COUNT(*), 0.75) FROM raw_prod.events) THEN 'Highly Engaged'
    WHEN u.action_count > (SELECT PERCENTILE_CONT(COUNT(*), 0.25) FROM raw_prod.events) THEN 'Moderately Engaged'
    ELSE 'Low Engagement'
  END AS engagement_level
FROM user_metrics u;

-- Problem: Correlated subqueries scan entire events table multiple times
```

**Optimized Query**:
```sql
-- Use APPROX_QUANTILES instead
WITH user_metrics AS (
  SELECT 
    user_id,
    COUNT(*) AS action_count,
    COUNT(DISTINCT DATE(event_timestamp)) AS active_days
  FROM raw_prod.events
  WHERE DATE(event_timestamp) >= DATE_SUB(CURRENT_DATE(), INTERVAL 90 DAY)
  GROUP BY user_id
),
percentiles AS (
  SELECT 
    APPROX_QUANTILES(action_count, 100)[OFFSET(75)] AS p75_actions,
    APPROX_QUANTILES(action_count, 100)[OFFSET(25)] AS p25_actions
  FROM user_metrics
)
SELECT 
  u.user_id,
  u.action_count,
  u.active_days,
  CASE 
    WHEN u.action_count > p.p75_actions THEN 'Highly Engaged'
    WHEN u.action_count > p.p25_actions THEN 'Moderately Engaged'
    ELSE 'Low Engagement'
  END AS engagement_level
FROM user_metrics u
CROSS JOIN percentiles p;

-- Optimization:
-- - Use APPROX_QUANTILES (1 scan) instead of correlated subqueries (N scans)
-- - CROSS JOIN single percentile row (no shuffle)
-- - Result: 10 seconds (vs. timeout)
```

## Troubleshooting & Monitoring

### 1. **Query Monitoring**

```python
# Get query stats
job = client.get_job(job_id)

print(f"Query: {job.query}")
print(f"State: {job.state}")
print(f"Started: {job.started}")
print(f"Ended: {job.ended}")
print(f"Duration: {(job.ended - job.started).total_seconds()} seconds")
print(f"Bytes scanned: {job.total_bytes_scanned / (1024**3):.2f} GB")
print(f"Bytes billed: {job.total_bytes_billed / (1024**3):.2f} GB")
print(f"Cache hit: {job.cache_hit}")
print(f"Slot milliseconds: {job.total_slot_ms}")

# Calculate cost
cost = (job.total_bytes_billed / (1024**4)) * 6.25  # $6.25 per TB
print(f"Estimated cost: ${cost:.4f}")
```

### 2. **Common Bottlenecks & Solutions**

| Bottleneck | Symptom | Solution |
|---|---|---|
| **Shuffle spike** | Bytes shuffled >> bytes scanned | Partition before join, pre-aggregate |
| **Slow aggregation** | Aggregation stage taking >50% time | Use approximate aggregations |
| **High memory** | OOM errors on workers | Reduce JOIN size, break into stages |
| **Long tail** | Few workers still processing | Uneven partition distribution, fix clustering |
| **Cache miss** | Query runs 60s, similar query 0.5s | Query differs (rewrite to match), cache expired |

```python
# Query audit logs for cost analysis
```

## Interview Questions & Scenarios

### Q1: "Optimize this query. It scans 50 GB daily but returns 1 KB."

```sql
-- Original slow query
SELECT DISTINCT customer_id FROM my_project.analytics_prod.transactions;
-- Scans: 50 GB, Returns: 1 KB (1 million distinct customers)
```

**Answer**:
1. Add partitioning: Reduce from 50 GB to daily chunks
2. Deduplicate earlier: Use APPROX_COUNT_DISTINCT
3. Cache results: Materialized view
4. Query incrementally: Only new customers since last run

```sql
-- Optimized
CREATE MATERIALIZED VIEW distinct_customers_cache AS
SELECT DISTINCT customer_id FROM my_project.raw_prod.transactions
WHERE DATE(timestamp) >= DATE_SUB(CURRENT_DATE(), INTERVAL 1 DAY);

-- Query: Scans only MV (few MB), instant results
```

### Q2: "Join fails with OOM. Both tables are 100 GB."

**Answer**:
1. Filter before join (reduce size)
2. Use broadcast join if one table can fit in memory
3. Break into multiple stages (join, aggregate, join again)
4. Use slot reservation for larger workers

### Q3: "BigQuery vs. Redshift. When choose BigQuery?"

**BigQuery wins**:
- No infrastructure management
- Pay per query (good for variable workloads)
- Petabyte scale without tuning
- Columnar performance
- Multi-region replication

**Redshift wins**:
- Predictable costs (annual slots cheaper)
- Isolated clusters (security/compliance)
- Complex stored procedures
