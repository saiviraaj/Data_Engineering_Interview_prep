### Layer Details

#### Layer 1: Landing (Bronze) - Raw Data Ingestion

```sql
-- Raw events table: Data as-is from source
CREATE TABLE my_project.landing_prod.raw_events_bronze (
  -- Source metadata
  ingestion_timestamp TIMESTAMP,
  source_system STRING,
  ingestion_batch_id STRING,
  
  -- Raw data (minimal transformation)
  raw_event JSON,
  raw_event_string STRING,
  
  -- Processing metadata
  file_path STRING,
  file_modification_time TIMESTAMP
)
PARTITION BY DATE(ingestion_timestamp)
CLUSTER BY source_system
OPTIONS(
  description = "Raw events landing, no transformation",
  require_partition_filter = true
);

-- Characteristics:
-- - Immutable (APPEND ONLY)
-- - Minimal schema (few columns)
-- - Retention: Long-term (2-3 years for audit)
-- - No data quality expectations
-- - Schema-on-read model
```

#### Layer 2: Processing (Silver) - Cleaned & Validated Data

```sql
-- Cleaned events table: Parsed, validated, deduplicated
CREATE TABLE my_project.staging_prod.processed_events_silver (
  -- Technical keys
  event_id STRING NOT NULL,
  source_system STRING NOT NULL,
  ingestion_batch_id STRING,
  
  -- Parsed event data
  user_id STRING NOT NULL,
  event_type STRING NOT NULL,
  event_timestamp TIMESTAMP NOT NULL,
  event_properties STRUCT<
    property_name STRING,
    property_value STRING,
    property_type STRING
  >,
  
  -- Validation metadata
  validation_timestamp TIMESTAMP,
  validation_passed BOOL,
  validation_errors ARRAY<STRING>,
  
  -- Deduplication
  dedup_flag BOOL,
  duplicate_count INT64,
  
  -- Lineage
  source_bronze_file STRING,
  processing_timestamp TIMESTAMP NOT NULL
)
PARTITION BY DATE(event_timestamp)
CLUSTER BY user_id, event_type
OPTIONS(
  description = "Cleaned and deduplicated events",
  require_partition_filter = true,
  partition_expiration_days = 730  -- 2 years
);

-- Characteristics:
-- - Deduplicated (no duplicates)
-- - Validated (quality checks passed)
-- - Schema-enforced (strong typing)
-- - Retention: Medium-term (1-2 years)
-- - Immutable (APPEND ONLY, never UPDATE)
```

## Data Vault & Dimensional Modeling

### Comparison: Star Schema vs. Data Vault

#### Star Schema (Dimensional Model)
Best for: BI and traditional analytics

```sql
-- Dimension table (slowly changing)
CREATE TABLE dim_customers (
  customer_key INT64 PRIMARY KEY,
  customer_id STRING NOT NULL,
  name STRING,
  email STRING,
  country STRING,
  signup_date DATE,
  scd_version INT64,
  valid_from DATE,
  valid_to DATE,
  is_current BOOL
);

-- Fact table (transaction events)
CREATE TABLE fact_sales (
  sale_key INT64 PRIMARY KEY,
  customer_key INT64,
  product_key INT64,
  store_key INT64,
  date_key INT64,
  sale_amount NUMERIC(12, 2),
  quantity INT64,
  discount_amount NUMERIC(12, 2)
);

-- Query (simple for BI)
SELECT 
  c.name,
  p.product_name,
  SUM(f.sale_amount) AS total_sales
FROM fact_sales f
JOIN dim_customers c ON f.customer_key = c.customer_key
JOIN dim_products p ON f.product_key = p.product_key
WHERE f.date_key >= 20240101
GROUP BY c.name, p.product_name;
```

**Advantages**:
- Simple queries (few JOINs)
- BI tools understand star schema
- Good for reporting

**Disadvantages**:
- Requires ETL for fact/dimension separation
- SCD logic complex (managing versions)
- Not flexible for exploratory analytics

#### Data Vault
Best for: Complex enterprise data, Agile analytics

```sql
-- Hub (Business keys)
CREATE TABLE hub_customer (
  customer_key INT64,
  customer_id STRING NOT NULL,
  load_dts TIMESTAMP,
  load_process STRING,
  rec_source STRING
);

-- Satellite (Attributes, slowly changing)
CREATE TABLE sat_customer_profile (
  customer_key INT64,
  load_dts TIMESTAMP,
  load_end_dts TIMESTAMP,
  is_current BOOL,
  name STRING,
  email STRING,
  country STRING,
  rec_source STRING,
  hash_diff STRING  -- Detects changes
);

-- Link (Relationships)
CREATE TABLE link_customer_product (
  link_key INT64,
  customer_key INT64,
  product_key INT64,
  load_dts TIMESTAMP,
  load_process STRING,
  rec_source STRING
);

-- Fact (Transactions)
CREATE TABLE fact_purchase (
  fact_key INT64,
  link_key INT64,
  customer_key INT64,
  transaction_dts TIMESTAMP,
  amount NUMERIC(12, 2),
  quantity INT64,
  load_dts TIMESTAMP
);

-- Query (more complex but more flexible)
SELECT 
  cp.name,
  SUM(fp.amount) AS total_sales
FROM fact_purchase fp
JOIN link_customer_product lcp ON fp.link_key = lcp.link_key
JOIN hub_customer hc ON lcp.customer_key = hc.customer_key
JOIN sat_customer_profile scp ON hc.customer_key = scp.customer_key
WHERE scp.is_current = TRUE
AND fp.transaction_dts >= CURRENT_TIMESTAMP() - INTERVAL 1 YEAR
GROUP BY cp.name;
```

**Advantages**:
- Tracks all history (audit trail)
- Flexible for changing business logic
- Supports agile development

**Disadvantages**:
- Complex queries (many JOINs)
- Steep learning curve
- Overkill for simple reporting

## Multi-Tenant Design Patterns

For Accenture Research, managing multiple research projects requires isolation:

### Pattern 1: Schema-Based Isolation

```sql
-- Separate schemas per tenant (research project)
CREATE SCHEMA project_01_climate_research;
CREATE SCHEMA project_02_ai_research;
CREATE SCHEMA project_03_sustainability_research;

-- Each project has own tables
CREATE TABLE project_01_climate_research.raw_weather_data (...);
CREATE TABLE project_02_ai_research.training_datasets (...);

-- Access control per schema
GRANT roles/bigquery.dataEditor ON SCHEMA project_01_climate_research 
TO group:climate-team@accenture.com;

-- Benefits:
-- - Clear isolation
-- - Easy backups per project
-- - Simple RBAC
-- - Clear cost attribution per project

-- Query across projects
SELECT 
  c.temperature,
  a.model_predictions
FROM project_01_climate_research.raw_weather_data c
CROSS JOIN project_02_ai_research.training_datasets a
WHERE c.date = '2024-01-15';
```

### Pattern 2: Column-Based Isolation (Row-Level Security)

```sql
-- Single shared table with RLS
CREATE TABLE research_data.datasets_shared (
  project_id STRING NOT NULL,
  dataset_id STRING NOT NULL,
  data STRUCT<...>,
  created_by STRING,
  is_public BOOL,
  created_timestamp TIMESTAMP
);

-- Create authorized view with RLS
CREATE OR REPLACE VIEW research_data.vw_datasets_secure AS
SELECT * FROM research_data.datasets_shared
WHERE 
  -- User can see own project's data
  project_id IN (
    SELECT project_id FROM research_data.user_projects 
    WHERE user_email = SESSION_USER()
  )
  -- OR data is marked public
  OR is_public = TRUE;

-- Grant view access only
GRANT roles/bigquery.dataViewer ON VIEW research_data.vw_datasets_secure 
TO group:all-researchers@accenture.com;

-- Benefits:
-- - Single source of truth
-- - Flexible sharing (public/private)
-- - Cost savings (shared infrastructure)
-- - Complex query logic possible

-- Challenge:
-- - More complex queries
-- - Performance overhead from filtering
```

## Real-Time Analytics Architecture

### Streaming Data Ingestion to BigQuery

```python
from google.cloud import bigquery_storage
import json
from datetime import datetime

# Use Cloud Pub/Sub for event streaming
import google.cloud.pubsub_v1 as pubsub

def stream_events_to_bigquery(project_id: str, topic: str):
    """Stream events from Pub/Sub to BigQuery"""
    
    client = bigquery.Client(project=project_id)
    table_id = f"{project_id}.analytics_prod.events_streaming"
    
    rows_to_insert = []
    
    def callback(message):
        # Parse incoming Pub/Sub message
        event = json.loads(message.data)
        
        # Enrich event
        row = {
            "event_id": event["id"],
            "user_id": event["user_id"],
            "event_type": event["type"],
            "event_timestamp": event["timestamp"],
            "ingestion_timestamp": datetime.utcnow().isoformat(),
            "properties": event.get("properties"),
            "source_system": "pubsub"
        }
        
        rows_to_insert.append(row)
        message.ack()
        
        # Batch insert (every 100 rows or 10 seconds)
        if len(rows_to_insert) >= 100:
            errors = client.insert_rows_json(table_id, rows_to_insert)
            if errors:
                print(f"Errors: {errors}")
            rows_to_insert.clear()
    
    subscriber = pubsub.SubscriberClient()
    subscription_path = subscriber.subscription_path(project_id, topic)
    
    streaming_pull_future = subscriber.subscribe(
        subscription_path, callback=callback
    )
    
    try:
        streaming_pull_future.result(timeout=600)
    except Exception as e:
        print(f"Error: {e}")
```

### Schema Evolution for Streaming Data

```sql
-- Streaming inserts allow schema evolution with new columns
CREATE TABLE my_project.analytics_prod.events_stream (
  event_id STRING,
  user_id STRING,
  event_type STRING,
  event_timestamp TIMESTAMP,
  ingestion_timestamp TIMESTAMP,
  
  -- Properties as JSON for flexibility
  properties JSON,
  
  -- Version tracking for schema evolution
  schema_version INT64,
  
  -- Processing metadata
  processing_timestamp TIMESTAMP GENERATED ALWAYS AS (CURRENT_TIMESTAMP())
)
PARTITION BY DATE(event_timestamp)
CLUSTER BY user_id, event_type;

-- Streaming insert with new properties
INSERT INTO my_project.analytics_prod.events_stream
SELECT 
  event_id,
  user_id,
  event_type,
  event_timestamp,
  CURRENT_TIMESTAMP(),
  -- Properties stored as JSON (schema-agnostic)
  JSON '{"property_name": "value"}',
  1,
  CURRENT_TIMESTAMP()
FROM pubsub_data;

-- Query nested properties
SELECT 
  event_id,
  user_id,
  JSON_EXTRACT_SCALAR(properties, '$.device') AS device,
  JSON_EXTRACT_SCALAR(properties, '$.version') AS app_version
FROM my_project.analytics_prod.events_stream;
```

### Backup Strategy

```python
from google.cloud import bigquery
from datetime import datetime, timedelta

def backup_critical_tables(project_id: str, dataset_id: str):
    """Backup critical tables with timestamp"""
    
    client = bigquery.Client(project=project_id)
    
    # Get all tables in dataset
    tables = client.list_tables(dataset_id)
    
    timestamp = datetime.utcnow().strftime("%Y%m%d_%H%M%S")
    backup_dataset_id = f"{dataset_id}_backup_{timestamp}"
    
    # Create backup dataset
    backup_dataset = bigquery.Dataset(backup_dataset_id)
    backup_dataset.location = "US"
    backup_dataset = client.create_dataset(backup_dataset)
    
    # Clone each table to backup
    for table in tables:
        table_id = table.table_id
        source_table_id = f"{project_id}.{dataset_id}.{table_id}"
        dest_table_id = f"{project_id}.{backup_dataset_id}.{table_id}"
        
        # Clone table (zero-copy, instant)
        job_config = bigquery.CopyJobConfig()
        job_config.write_disposition = bigquery.WriteDisposition.WRITE_TRUNCATE
        
        copy_job = client.copy_table(
            source_table_id,
            dest_table_id,
            job_config=job_config
        )
        copy_job.result()
        
    print(f"Backup created: {backup_dataset_id}")
    
    # Delete old backups (older than 30 days)
    max_age = datetime.utcnow() - timedelta(days=30)
    for dataset in client.list_datasets():
        if dataset.dataset_id.startswith(f"{dataset_id}_backup_"):
            # Extract date from backup dataset name
            date_str = dataset.dataset_id.split("_")[-2] + "_" + dataset.dataset_id.split("_")[-1]
            backup_date = datetime.strptime(date_str, "%Y%m%d_%H%M%S")
            
            if backup_date < max_age:
                client.delete_dataset(dataset.dataset_id, delete_contents=True)
```

## Interview Design Questions

### Q1: "Design a data architecture for Accenture's 100+ data sources."

**Expected Answer Structure**:

1. **Ingestion Strategy**:
   - Multiple ingestion patterns (batch, streaming, API)
   - Source-specific connectors (Dataflow, Cloud Composer, Cloud Run)
   - Standardized metadata capture (source, timestamp, version)

2. **Landing Layer**:
   - Minimal transformation, schema-on-read
   - Raw data lake in GCS + BigQuery external tables
   - Immutable, append-only design
   - Cost-optimized retention (cold storage after 90 days)

3. **Processing Layer**:
   - Data quality validation
   - Deduplication & reconciliation
   - Standardized data models (dbt)
   - Slowly Changing Dimension (SCD) handling

4. **Analytics Layer**:
   - Dimensional modeling or Data Vault based on use case
   - Research-specific aggregations (features for ML)
   - Efficient partitioning/clustering
   - Materialized views for repeated queries

5. **Governance**:
   - Project registry (data lineage, ownership)
   - Access control per research team
   - Data classification (public/internal/confidential)
   - Quality metrics & monitoring

### Q2: "How would you support 60+ research projects with isolated data?"

**Answer**:
Use hybrid approach:
- **Shared raw layer**: Centralized data ingestion
- **Project-specific datasets**: Isolated landing/staging/analytics per project
- **Column-level security**: For sensitive data sharing
- **Cost attribution**: BigQuery logs track usage per project
- **Federated access**: Views bridge shared + isolated data

### Q3: "Design a real-time analytics system for research."

**Answer**:
