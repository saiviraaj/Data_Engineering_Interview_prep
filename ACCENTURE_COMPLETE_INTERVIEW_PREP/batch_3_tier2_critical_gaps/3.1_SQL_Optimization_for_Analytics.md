## Query Optimization Fundamentals

### Query Optimization Lifecycle

```
┌─────────────────────────────────────────┐
│ 1. WRITE QUERY (Inefficient)            │
│    SELECT * FROM huge_table WHERE ...   │
└────────────┬────────────────────────────┘
             ↓
┌─────────────────────────────────────────┐
│ 2. ANALYZE PERFORMANCE                  │
│    - Execution time: 120 seconds        │
│    - Data scanned: 500 GB               │
│    - Rows processed: 1 billion          │
└────────────┬────────────────────────────┘
             ↓
┌─────────────────────────────────────────┐
│ 3. IDENTIFY BOTTLENECK                  │
│    - Full table scan (no partition)     │
│    - Multiple JOINs (shuffle)           │
│    - SELECT * (unnecessary columns)     │
└────────────┬────────────────────────────┘
             ↓
┌─────────────────────────────────────────┐
│ 4. OPTIMIZE                             │
│    - Add partition filter               │
│    - Reorder JOINs                      │
│    - Select only needed columns         │
└────────────┬────────────────────────────┘
             ↓
┌─────────────────────────────────────────┐
│ 5. VERIFY & MEASURE                     │
│    - Execution time: 5 seconds (24x!)   │
│    - Data scanned: 20 GB (25x less!)    │
│    - Cost: $0.09 → $0.004 (22x cheaper)│
└─────────────────────────────────────────┘
```

### Common Performance Anti-Patterns

```sql
-- ❌ ANTI-PATTERN 1: SELECT *
SELECT * FROM huge_table WHERE date = '2024-01-15';
-- Scans ALL columns even if you only need 5
-- 500 GB → 50 GB with column projection

-- ✅ GOOD: Select only needed columns
SELECT customer_id, amount, date FROM huge_table 
WHERE date = '2024-01-15';

-- ❌ ANTI-PATTERN 2: No partition filtering
SELECT COUNT(*) FROM events;
-- Scans entire history (5 years of data)

-- ✅ GOOD: Partition filter
SELECT COUNT(*) FROM events 
WHERE DATE(event_timestamp) = CURRENT_DATE();

-- ❌ ANTI-PATTERN 3: Correlated subqueries
SELECT customer_id, name, 
       (SELECT COUNT(*) FROM orders o WHERE o.customer_id = c.customer_id) as order_count
FROM customers c;
-- Subquery runs once per customer row (1M queries for 1M rows!)

-- ✅ GOOD: GROUP BY + LEFT JOIN
SELECT c.customer_id, c.name, COUNT(o.order_id) as order_count
FROM customers c
LEFT JOIN orders o ON c.customer_id = o.customer_id
GROUP BY c.customer_id, c.name;

-- ❌ ANTI-PATTERN 4: Joining large tables without filtering
SELECT * FROM table_a JOIN table_b ON table_a.id = table_b.id;
-- If both tables 100 GB, shuffle is 200 GB

-- ✅ GOOD: Filter before join
SELECT * FROM (
  SELECT * FROM table_a WHERE important_flag = true
) a
JOIN (
  SELECT * FROM table_b WHERE status = 'active'
) b ON a.id = b.id;

-- ❌ ANTI-PATTERN 5: GROUP BY on large dimension
SELECT customer_demographic, SUM(amount)
FROM transactions
GROUP BY customer_demographic;
-- Shuffle cost = table size (expensive)

-- ✅ GOOD: Pre-aggregate or use approx functions
SELECT customer_demographic, APPROX_SUM(amount)
FROM transactions
GROUP BY customer_demographic;
-- Much faster, good enough for 99% of use cases
```

## Execution Plans & Analysis

### Reading Execution Plans (BigQuery)

```sql
-- Example query to analyze
SELECT 
  DATE(order_date) as order_date,
  product_category,
  SUM(amount) as total_sales,
  COUNT(DISTINCT customer_id) as unique_customers
FROM transactions
WHERE DATE(order_date) = '2024-01-15'
GROUP BY order_date, product_category
ORDER BY total_sales DESC;

-- Execution Plan Output:
-- Stage 0: Table Scan (transactions)
--   ├─ Table: my-project:my_dataset.transactions
--   ├─ Data scanned: 2 GB (full partition for 2024-01-15)
--   ├─ Rows read: 50 million
--   ├─ Bytes scanned: 2,000,000,000
--   └─ Time: 3.2 seconds
--
-- Stage 1: Hash Aggregation
--   ├─ Input rows: 50 million
--   ├─ Output rows: 1,500 (product categories)
--   ├─ Aggregations: SUM(amount), COUNT(DISTINCT customer_id)
--   ├─ Shuffle bytes: 150 MB
--   └─ Time: 2.5 seconds
--
-- Stage 2: Sort
--   ├─ Input rows: 1,500
--   ├─ Output rows: 1,500
--   ├─ Shuffle bytes: 150 KB
--   └─ Time: 0.3 seconds
--
-- Total: Data scanned 2 GB, Shuffle 150 MB, Time 6 seconds, Cost $0.0125

-- Key Metrics:
-- • Bytes scanned: Should minimize (partition filter helps)
-- • Bytes shuffled: Should minimize (aggregate before shuffle)
-- • Execution time: Should minimize (parallelize, reduce shuffle)
-- • Cost: Bytes scanned / 1 TB * $6.25
```

### Query Plan Interpretation

```
BOTTLENECK ANALYSIS:

If Stage 0 (Table Scan) takes 80% of time:
→ Problem: Too much data scanned
→ Solution: Add partition filter, cluster filter, or both
→ Example: Add WHERE DATE(timestamp) >= '2024-01-01'

If Stage 1 (Aggregation) takes 80% of time:
→ Problem: Large shuffle operation
→ Solution: Pre-aggregate, use approximate functions, filter before agg
→ Example: GROUP BY fewer dimensions, or APPROX_COUNT_DISTINCT

If you see "Shuffle bytes >> Data scanned":
→ Problem: JOIN or GROUP BY amplifying data
→ Solution: Filter before join, use broadcast join for small tables
→ Example: Filter large table first, then JOIN with small lookup

If execution time doesn't improve with optimization:
→ Problem: Might be compilation or queuing overhead
→ Solution: Run query multiple times (BigQuery caches), combine multiple queries
```

## Advanced SQL Patterns

### 1. Window Functions (Best Practices)

```sql
-- Problem: Calculate running total per customer per month
SELECT 
  customer_id,
  DATE_TRUNC(order_date, MONTH) as month,
  amount,
  SUM(amount) OVER (
    PARTITION BY customer_id, DATE_TRUNC(order_date, MONTH)
    ORDER BY order_date
    ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW
  ) as running_total
FROM orders
WHERE order_date >= DATE_SUB(CURRENT_DATE(), INTERVAL 12 MONTH)
ORDER BY customer_id, order_date;

-- Key optimizations:
-- 1. PARTITION BY reduces computation (local per partition, not global)
-- 2. ORDER BY must align with window frame
-- 3. Use ROWS BETWEEN instead of RANGE (ROWS is faster)

-- Performance comparison:
-- Window function: 10 seconds (single pass through data)
-- Self-join approach: 300 seconds (multiple scans)
```

### 2. Common Table Expressions (CTEs)

```sql
-- Good CTE: Reduces complexity, helps optimizer
WITH customer_monthly_spend AS (
  SELECT 
    customer_id,
    DATE_TRUNC(order_date, MONTH) as month,
    SUM(amount) as total_spend,
    COUNT(*) as order_count
  FROM orders
  WHERE order_date >= DATE_SUB(CURRENT_DATE(), INTERVAL 24 MONTH)
  GROUP BY customer_id, month
),

customer_summary AS (
  SELECT
    customer_id,
    AVG(total_spend) as avg_monthly_spend,
    MAX(total_spend) as max_monthly_spend,
    MIN(total_spend) as min_monthly_spend,
    SUM(order_count) as lifetime_orders
  FROM customer_monthly_spend
  GROUP BY customer_id
)

SELECT 
  cs.customer_id,
  cs.avg_monthly_spend,
  cs.max_monthly_spend,
  cs.lifetime_orders,
  c.segment
FROM customer_summary cs
JOIN customer_segments c ON cs.customer_id = c.customer_id
WHERE cs.lifetime_orders > 10
ORDER BY cs.avg_monthly_spend DESC;

-- Optimization notes:
-- 1. BigQuery pushes filters down through CTEs
-- 2. Use CTEs to break complex queries (clarity + performance)
-- 3. CTEs not always materialized (no overhead)
```

### 3. UNION vs. UNION ALL

```sql
-- ❌ UNION (removes duplicates - expensive!)
SELECT user_id FROM table_a
UNION
SELECT user_id FROM table_b;
-- BigQuery must:
-- 1. Scan both tables
-- 2. Deduplicate across both
-- 3. Cost: 2x scans + dedup overhead

-- ✅ UNION ALL (keeps duplicates - fast!)
SELECT user_id FROM table_a
UNION ALL
SELECT user_id FROM table_b;
-- BigQuery:
-- 1. Scans both tables
-- 2. Concatenates (no dedup)
-- 3. Cost: Just 2x scans

-- If dedup needed:
-- ✅ GROUP BY (explicit, clear)
SELECT user_id 
FROM (
  SELECT user_id FROM table_a
  UNION ALL
  SELECT user_id FROM table_b
)
GROUP BY user_id;
```

### 4. Recursive CTEs (Use Carefully)

```sql
-- Use case: Hierarchical data (org chart, categories)
WITH RECURSIVE org_hierarchy AS (
  -- Base case: top-level managers
  SELECT 
    employee_id,
    name,
    manager_id,
    1 as level
  FROM employees
  WHERE manager_id IS NULL
  
  UNION ALL
  
  -- Recursive case: subordinates
  SELECT 
    e.employee_id,
    e.name,
    e.manager_id,
    oh.level + 1
  FROM employees e
  JOIN org_hierarchy oh ON e.manager_id = oh.employee_id
  WHERE oh.level < 10  -- Limit recursion depth
)

SELECT * FROM org_hierarchy
ORDER BY level, employee_id;

-- WARNING: Recursive CTEs can be slow if not bounded!
-- Always include a termination condition (level limit, path limit)
```

## BigQuery-Specific Optimization

### 1. Clustering Strategy

```sql
-- Table design: Event data for multiple use cases
CREATE TABLE events (
  event_id STRING NOT NULL,
  user_id STRING NOT NULL,
  event_type STRING NOT NULL,
  event_timestamp TIMESTAMP NOT NULL,
  properties JSON,
  value NUMERIC(12, 2)
)
PARTITION BY DATE(event_timestamp)
CLUSTER BY user_id, event_type;

-- Query 1: Events for specific user + type
SELECT *
FROM events
WHERE DATE(event_timestamp) = '2024-01-15'
  AND user_id = 'user123'
  AND event_type = 'purchase';
-- Scans: Only 1 day partition + user123's blocks + purchase type blocks
-- Time: Sub-second

-- Query 2: Top events across users
SELECT event_type, COUNT(*) as count
FROM events
WHERE DATE(event_timestamp) >= '2024-01-01'
GROUP BY event_type;
-- Scans: All partitions, but grouped by cluster (efficient grouping)
-- Time: Few seconds

-- Query 3: Date range query (not clustered)
SELECT COUNT(*)
FROM events
WHERE DATE(event_timestamp) BETWEEN '2024-01-01' AND '2024-03-31'
  AND value > 100;
-- Scans: 3 months of partitions (partition prunes)
-- Time: Moderate (clustering doesn't help, but partition does)
```

### 2. Materialized Views for Repeated Queries

```sql
-- Expensive base query
SELECT 
  DATE(order_date) as order_date,
  customer_id,
  product_category,
  SUM(amount) as daily_sales,
  COUNT(*) as order_count,
  COUNT(DISTINCT order_id) as unique_orders
FROM orders
WHERE order_date >= DATE_SUB(CURRENT_DATE(), INTERVAL 365 DAY)
GROUP BY order_date, customer_id, product_category;

-- Create materialized view (pre-aggregated)
CREATE MATERIALIZED VIEW daily_sales_by_customer AS
SELECT 
  DATE(order_date) as order_date,
  customer_id,
  product_category,
  SUM(amount) as daily_sales,
  COUNT(*) as order_count,
  COUNT(DISTINCT order_id) as unique_orders
FROM orders
WHERE order_date >= DATE_SUB(CURRENT_DATE(), INTERVAL 365 DAY)
GROUP BY order_date, customer_id, product_category;

-- Queries against MV are instant
SELECT * FROM daily_sales_by_customer
WHERE order_date = '2024-01-15'
  AND customer_id = 'cust123';
-- Scans: Only 1 row (pre-aggregated)
-- Cost: Near zero

-- BigQuery automatically rewrites queries to use MV when applicable
SELECT 
  product_category,
  SUM(daily_sales) as total_sales
FROM daily_sales_by_customer
WHERE order_date = '2024-01-15'
GROUP BY product_category;
-- BigQuery: "Oh, I can use the MV!" → Instant response
```

### 3. Approximate Aggregations

```sql
-- Exact (Expensive): DISTINCT count of 1 billion rows
SELECT COUNT(DISTINCT user_id) as unique_users
FROM events;
-- Time: 30+ seconds
-- Cost: Scans entire table

-- Approximate (Fast): 1-2% error, 100x faster
SELECT APPROX_COUNT_DISTINCT(user_id) as approx_unique_users
FROM events;
-- Time: 2-3 seconds
-- Cost: Much lower

-- Percentile estimation (instead of full sort)
SELECT 
  APPROX_QUANTILES(amount, 100)[OFFSET(50)] as p50_amount,
  APPROX_QUANTILES(amount, 100)[OFFSET(95)] as p95_amount,
  APPROX_QUANTILES(amount, 100)[OFFSET(99)] as p99_amount
FROM transactions;
-- Exact would require sorting 1 billion rows (very slow)
-- Approx gives result in seconds

-- Top-K estimation (instead of full aggregation)
SELECT 
  product_id,
  revenue
FROM (
  SELECT 
    product_id,
    SUM(amount) as revenue
  FROM orders
  GROUP BY product_id
)
ORDER BY revenue DESC
LIMIT 100;

-- Use APPROX_TOP_COUNT for huge datasets
SELECT 
  product_id,
  revenue
FROM (
  SELECT 
    product_id,
    SUM(amount) as revenue
  FROM orders
  GROUP BY product_id
)
ORDER BY revenue DESC
LIMIT 100;
-- For 100M products: Exact = 5 min, Approx = 5 sec
```

## Window Functions & CTEs

### 1. Ranking & Dense Ranking

```sql
-- Find top 3 products per category
SELECT 
  product_category,
  product_name,
  revenue,
  rank,
  dense_rank,
  row_number
FROM (
  SELECT 
    product_category,
    product_name,
    revenue,
    ROW_NUMBER() OVER (
      PARTITION BY product_category
      ORDER BY revenue DESC
    ) as row_number,
    RANK() OVER (
      PARTITION BY product_category
      ORDER BY revenue DESC
    ) as rank,
    DENSE_RANK() OVER (
      PARTITION BY product_category
      ORDER BY revenue DESC
    ) as dense_rank
  FROM products
)
WHERE row_number <= 3;

-- Difference:
-- ROW_NUMBER: 1, 2, 3 (always consecutive)
-- RANK: 1, 1, 3 (gaps if ties)
-- DENSE_RANK: 1, 1, 2 (no gaps)
```

### 2. LAG & LEAD

```sql
-- Month-over-month comparison
SELECT 
  month,
  sales,
  LAG(sales) OVER (ORDER BY month) as prev_month_sales,
  LEAD(sales) OVER (ORDER BY month) as next_month_sales,
  ROUND(100 * (sales - LAG(sales) OVER (ORDER BY month)) 
        / LAG(sales) OVER (ORDER BY month), 2) as mom_growth_pct
FROM monthly_sales
ORDER BY month;

-- Output:
-- month       sales   prev    next   growth
-- 2024-01-01  100000  NULL    95000  NULL
-- 2024-02-01  95000   100000  108000 -5.00%
-- 2024-03-01  108000  95000   NULL   13.68%
```

### 3. FIRST_VALUE & LAST_VALUE

```sql
-- Customer lifecycle analysis
SELECT 
  customer_id,
  order_date,
  amount,
  FIRST_VALUE(amount) OVER (
    PARTITION BY customer_id
    ORDER BY order_date
  ) as first_order_amount,
  LAST_VALUE(amount) OVER (
    PARTITION BY customer_id
    ORDER BY order_date
    ROWS BETWEEN UNBOUNDED PRECEDING AND UNBOUNDED FOLLOWING
  ) as last_order_amount
FROM orders
WHERE order_date >= '2024-01-01';

-- Note: LAST_VALUE requires ROWS BETWEEN ... UNBOUNDED FOLLOWING
-- Without it, it defaults to "UNBOUNDED PRECEDING TO CURRENT ROW"
```

## Real-World Case Studies

### Case Study 1: Optimizing Slow Dashboard Query

**Before (60 seconds, $0.38 cost):**
```sql
SELECT 
  customer_id,
  customer_name,
  COUNT(*) as order_count,
  SUM(amount) as total_amount,
  AVG(amount) as avg_amount
FROM orders
WHERE amount > 0
GROUP BY customer_id, customer_name
HAVING COUNT(*) > 5
ORDER BY total_amount DESC;
```

**Issues:**
- Full table scan (no date filter)
- SELECT * unnecessary columns before GROUP BY
- HAVING filter post-aggregation (expensive)

**After (2 seconds, $0.006 cost):**
```sql
SELECT 
  customer_id,
  customer_name,
  COUNT(*) as order_count,
  SUM(amount) as total_amount,
  ROUND(AVG(amount), 2) as avg_amount
FROM orders
WHERE DATE(order_date) >= DATE_SUB(CURRENT_DATE(), INTERVAL 90 DAY)
  AND amount > 0
  AND customer_id IS NOT NULL
GROUP BY customer_id, customer_name
HAVING COUNT(*) > 5
ORDER BY total_amount DESC;
```

**Improvements:**
- Added partition filter (90 days → reduces 365 days of data)
- Removed SELECT * (only needed columns)
- Pre-filter WHERE amount > 0 (before GROUP BY)
- 30x faster, 63x cheaper

### Case Study 2: Handling Skewed Data

**Problem: One customer dominates GROUP BY**

```sql
-- 1 million customers, but customer_id='HUGE_CORP' has 50% of data
SELECT 
  customer_id,
  COUNT(*) as order_count
FROM orders
GROUP BY customer_id;

-- This skewed aggregation can be slow because one worker handles HUGE_CORP
-- Other workers finish quickly, then wait for HUGE_CORP worker
```

**Solution: Handle hot key separately**

```sql
WITH hot_key_orders AS (
  -- Handle hot key in separate query
  SELECT 
    customer_id,
    COUNT(*) as order_count
  FROM orders
  WHERE customer_id = 'HUGE_CORP'
  GROUP BY customer_id
),

other_customer_orders AS (
  -- Handle all others
  SELECT 
    customer_id,
    COUNT(*) as order_count
  FROM orders
  WHERE customer_id != 'HUGE_CORP'
  GROUP BY customer_id
)

SELECT * FROM hot_key_orders
UNION ALL
SELECT * FROM other_customer_orders;

-- Result: Both queries finish in parallel, no worker starvation
```

## Interview Questions

### Q1: "This query takes 30 seconds. How would you optimize?"

```sql
SELECT c.customer_id, c.name, COUNT(o.order_id) as order_count
FROM customers c
JOIN orders o ON c.customer_id = o.customer_id
WHERE YEAR(o.order_date) = 2024
GROUP BY c.customer_id, c.name
ORDER BY order_count DESC;
```

**Answer Steps:**
1. **Analyze the query**:
   - JOIN without filter (both tables scanned)
   - YEAR() function prevents partition pruning
   - No clustering info

2. **Optimize**:
```sql
SELECT c.customer_id, c.name, COUNT(o.order_id) as order_count
FROM customers c
JOIN orders o ON c.customer_id = o.customer_id
WHERE o.order_date >= '2024-01-01' AND o.order_date < '2025-01-01'
GROUP BY c.customer_id, c.name
ORDER BY order_count DESC;
```

3. **Further optimizations**:
   - Filter orders before JOIN
   - If customers table is small, broadcast it
   - Use APPROX_COUNT_DISTINCT if exact count not needed

### Q2: "Design SQL for 100+ metric dashboard."

**Answer**: Use materialized views
- One MV per metric
- Updated daily/hourly
- Queries hit MV (instant)
- Cost: Storage only, no query cost

### Q3: "Query scans 500 GB but returns 1 KB. Fix?"

**Answer**: 
- Partition filter missing
- Column projection (SELECT *)
- Clustering opportunity
- Approximate aggregation if applicable
