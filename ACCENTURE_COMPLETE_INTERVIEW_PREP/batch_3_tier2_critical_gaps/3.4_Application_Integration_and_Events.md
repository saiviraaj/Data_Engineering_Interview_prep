## Integration Fundamentals

### Integration Challenges

```
Enterprise Integration:

Without Integration:
  System A    System B    System C
    │           │           │
    └─────────────────────────┘
          (No communication)
    → Data silos
    → Manual processes
    → Inconsistent data

With Integration:
  System A ←→ Integration Hub ←→ System B
                     │
                  System C
    → Unified data flow
    → Automated processes
    → Single source of truth
```

### Integration Patterns

```
1. FILE TRANSFER
   System A → Writes file → System B reads
   Pros: Simple, decoupled
   Cons: Batch (not real-time), latency

2. SHARED DATABASE
   System A → Direct write → Shared DB ← System B reads
   Pros: Real-time, consistent
   Cons: Tight coupling, single point of failure

3. MESSAGING/EVENTS
   System A → Sends event → Message Queue ← System B listens
   Pros: Decoupled, scalable, real-time
   Cons: Complexity, eventual consistency

4. API-BASED
   System A → HTTP/gRPC call → System B
   Pros: Clear contracts, synchronous
   Cons: Tight coupling, latency
```

## Event-Driven Architecture

### Event-Driven Principles

```
Event = Something important happened

Example: "User Clicked Purchase Button"
  ├─ Event Type: order.created
  ├─ Timestamp: 2024-04-11T12:34:56Z
  ├─ User ID: user123
  ├─ Order ID: order456
  └─ Metadata: {items: [...], total: 199.99}

Event Producers (Generate events)
  ├─ User actions (clicks, scrolls)
  ├─ System events (errors, deployments)
  ├─ Data changes (record updates)
  └─ Third-party webhooks

Event Consumers (React to events)
  ├─ Notifications (email, SMS)
  ├─ Analytics (track user behavior)
  ├─ Data sync (update other systems)
  └─ Workflows (trigger automations)

Event Bus (Mediates between producers & consumers)
  ├─ Cloud Pub/Sub
  ├─ Kafka
  ├─ Cloud Tasks
  └─ Message Queue
```

### Event-Driven Benefits

```
1. DECOUPLING
   System A doesn't know about System B
   → Can evolve independently
   → Easier to add/remove systems

2. SCALABILITY
   Multiple consumers can listen to same event
   → Linear scaling
   → No bottleneck

3. REAL-TIME
   Events processed immediately
   → Seconds latency (not hours)
   → Responsive systems

4. AUDITABILITY
   All events logged
   → Complete audit trail
   → Can replay history
```

## Pub/Sub Patterns

### Cloud Pub/Sub Architecture

```
┌──────────────────────────────────────┐
│        EVENT PRODUCERS               │
│  - User actions                      │
│  - System events                     │
│  - Data changes                      │
└──────────────┬───────────────────────┘
               │ (Publish event)
               ↓
       ┌───────────────────┐
       │   Cloud Pub/Sub   │
       │   (Message Broker)│
       │  - Topic: events  │
       │  - Subscriptions: │
       │    * sub-1        │
       │    * sub-2        │
       │    * sub-3        │
       └──────────┬────────┘
    ┌──────┬──────┴──────┐
    ↓      ↓             ↓
  ┌─────┐ ┌──────┐  ┌─────────┐
  │ App1 │ │ App2 │  │ Dataflow│
  │(Pull)│ │(Push)│  │(Stream) │
  └─────┘ └──────┘  └─────────┘
```

### Pub/Sub Implementation

```python
from google.cloud import pubsub_v1
import json
from datetime import datetime

class EventProducer:
    def __init__(self, project_id: str, topic_id: str):
        self.publisher = pubsub_v1.PublisherClient()
        self.topic_path = self.publisher.topic_path(project_id, topic_id)
    
    def publish_event(self, event_type: str, data: dict):
        """Publish event to topic"""
        
        event = {
            'event_type': event_type,
            'timestamp': datetime.utcnow().isoformat(),
            'data': data
        }
        
        message_json = json.dumps(event)
        message_bytes = message_json.encode('utf-8')
        
        future = self.publisher.publish(
            self.topic_path,
            data=message_bytes,
            event_type=event_type  # Attributes for filtering
        )
        
        print(f"Published {event_type}: {future.result()}")

class EventConsumer:
    def __init__(self, project_id: str, subscription_id: str):
        self.subscriber = pubsub_v1.SubscriberClient()
        self.subscription_path = self.subscriber.subscription_path(
            project_id, subscription_id
        )
    
    def handle_message(self, message: pubsub_v1.types.PubsubMessage):
        """Process incoming message"""
        
        try:
            event = json.loads(message.data)
            event_type = event['event_type']
            
            # Route to handler based on event type
            if event_type == 'order.created':
                self.on_order_created(event['data'])
            elif event_type == 'user.registered':
                self.on_user_registered(event['data'])
            elif event_type == 'payment.completed':
                self.on_payment_completed(event['data'])
            
            # Acknowledge message
            message.ack()
            
        except Exception as e:
            print(f"Error processing message: {e}")
            message.nack()  # Don't acknowledge, retry later
    
    def on_order_created(self, data):
        print(f"Processing order: {data}")
        # Could send email, update inventory, etc.
    
    def on_user_registered(self, data):
        print(f"New user registered: {data['email']}")
        # Could send welcome email, create account in other systems
    
    def on_payment_completed(self, data):
        print(f"Payment received: {data['amount']}")
        # Could update accounting system, send receipt
    
    def subscribe(self):
        """Start listening for messages"""
        streaming_pull_future = self.subscriber.subscribe(
            self.subscription_path,
            callback=self.handle_message
        )
        
        try:
            streaming_pull_future.result()
        except KeyboardInterrupt:
            streaming_pull_future.cancel()

# Usage
producer = EventProducer("my-project", "research-events")

# Publish events
producer.publish_event('experiment.started', {
    'experiment_id': 'exp123',
    'researcher': 'john@company.com'
})

producer.publish_event('experiment.completed', {
    'experiment_id': 'exp123',
    'duration_minutes': 120,
    'result': 'success'
})

# Subscribe to events
consumer = EventConsumer("my-project", "research-subscription")
consumer.subscribe()
```

### Pub/Sub Patterns

#### Pattern 1: Fan-Out

```
One event → Multiple consumers

Producer publishes: experiment.completed
  ├─ Consumer 1: Send notification email
  ├─ Consumer 2: Update dashboard
  ├─ Consumer 3: Trigger downstream analysis
  └─ Consumer 4: Log to analytics

Implementation:
- Single topic (experiment-events)
- Multiple subscriptions (one per consumer)
- Independent processing
```

#### Pattern 2: Event Sourcing

```
Store all events, reconstruct state

Event Log:
1. experiment.created (id: exp1, status: draft)
2. experiment.configured (id: exp1, params: {...})
3. experiment.started (id: exp1, start_time: ...)
4. experiment.checkpoint (id: exp1, progress: 50%)
5. experiment.completed (id: exp1, result: success)

Rebuild state:
Start with empty → Apply event 1 → Apply event 2 → ... 
Result: Complete experiment state + full history

Benefits:
- Complete audit trail
- Can replay to any point in time
- Debugging (what changed when?)
```

#### Pattern 3: Dead-Letter Queue (Error Handling)

```
Main Topic → Consumer
    ↓ (Success)
  Process

    ↓ (Error 1x)
  Retry

    ↓ (Error 2x)
  Retry

    ↓ (Error 3x)
  Dead-Letter Queue → Manual investigation
```

## System Integration Patterns

### Integration with Third-Party Services

```python
# Example: Integrating external data provider

class DataProviderClient:
    """Adapter for external data provider"""
    
    def __init__(self, api_key: str):
        self.api_key = api_key
        self.base_url = "https://api.dataprovider.com/v1"
    
    def fetch_data(self, dataset_id: str, filters: dict = None):
        """Fetch data from external provider"""
        import requests
        
        headers = {'Authorization': f'Bearer {self.api_key}'}
        params = filters or {}
        
        response = requests.get(
            f"{self.base_url}/datasets/{dataset_id}/data",
            headers=headers,
            params=params,
            timeout=30
        )
        
        if response.status_code != 200:
            raise Exception(f"API error: {response.text}")
        
        return response.json()
    
    def subscribe_to_updates(self, dataset_id: str, callback):
        """Subscribe to dataset updates via webhook"""
        webhook_url = "https://mycompany.com/webhooks/data-updates"
        
        payload = {
            'dataset_id': dataset_id,
            'callback_url': webhook_url,
            'events': ['data.updated', 'data.deleted']
        }
        
        response = requests.post(
            f"{self.base_url}/subscriptions",
            json=payload,
            headers={'Authorization': f'Bearer {self.api_key}'}
        )
        
        return response.json()

# Handle webhook updates
from flask import Flask, request

    })
    
    return {'status': 'received'}, 200
```

## Interview Questions

### Q1: "Design event-driven system for research platform."

**Answer:**
1. Events: experiment.created, experiment.completed, result.recorded
2. Producer: Experiment service publishes events
3. Queue: Cloud Pub/Sub (reliable, scalable)
4. Consumers: Notifications, dashboards, BigQuery, ML pipeline
5. Benefits: Decoupled, scalable, audit trail

### Q2: "How to integrate with external data provider?"

**Answer:**
1. Use API or webhook
2. Implement retry logic (circuit breaker)
3. Publish internal event for consistency
4. Store in datalake
5. Monitor latency, errors

### Q3: "Design API for research platform."

**Answer:**
1. REST for external (JSON, standard)
2. gRPC for internal (fast, binary)
3. Events via Pub/Sub (async)
4. GraphQL for flexible queries
5. Clear versioning, documentation
