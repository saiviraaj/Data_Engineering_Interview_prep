## AlloyDB Introduction

### What is AlloyDB?

**AlloyDB** is Google Cloud's fully managed relational database service built on PostgreSQL. It combines:
- **PostgreSQL compatibility** (easier migration)
- **Google Cloud scalability** (horizontal read replicas)
- **Cloud native features** (automated backups, high availability)
- **Superior performance** (2.5x faster than open-source PostgreSQL)

### Strategic Positioning

```
DATABASE LANDSCAPE:

┌────────────────────────────────────────────────────┐
│  OLTP (Online Transaction Processing)             │
│  - Many small reads/writes                        │
│  - Real-time data                                  │
│  - Strict ACID requirements                        │
│  - Examples: Production apps, payments             │
│                                                     │
│  Solution: Cloud SQL, AlloyDB                      │

┌────────────────────────────────────────────────────┐
```

### AlloyDB Cluster Architecture

```
┌─────────────────────────────────────────────────────┐
│        ALLODYDB CLUSTER (Primary Region)            │
├─────────────────────────────────────────────────────┤
│                                                     │
│  PRIMARY (Write)                                    │
│  ┌──────────────────────────────────────────────┐  │
│  │ Instance: 4 vCPU, 15 GB Memory              │  │

│  │ - Replicate to secondaries                  │  │
│  └──────────────────────────────────────────────┘  │
│                                                     │
│  SECONDARY REPLICAS (Read-Only)                    │
│  ┌──────────────────────────────────────────────┐  │
│  │ Instance 1: 2 vCPU, 8 GB Memory (in region) │  │
│  │ Instance 2: 2 vCPU, 8 GB Memory (in region) │  │

│  │ - High availability failover                │  │

│                                                     │

         ↓ (Cross-region replication)
┌─────────────────────────────────────────────────────┐

```

```
                     (Write queries, 
                      Transactions)

                     (Read-only queries,
                      Geographic distribution)

Load Balancer ────→ Route reads to nearest replica
```

## AlloyDB vs. BigQuery vs. Cloud SQL

### Feature Comparison Matrix

| Feature | AlloyDB | BigQuery | Cloud SQL (MySQL/Postgres) |
|---------|---------|----------|---|
| **Type** | OLTP/Relational | OLAP/Data Warehouse | Traditional OLTP |
| **Use Case** | Production apps | Analytics | Legacy apps |
| **Query Latency** | <1 second | Seconds | <1 second |
| **Data Scale** | TB | PB | GB-TB |
| **Writes** | ✅ Real-time | ❌ Streaming/Batch | ✅ Real-time |
| **Transactions** | ✅ Full ACID | ❌ Limited | ✅ Full ACID |
| **Scaling** | Read replicas | Automatic | Manual |
| **Cost** | Per instance + storage | Per TB scanned | Per instance |
| **Admin** | Fully managed | Fully managed | Fully managed |

### When to Use Each

```
DECISION TREE:

Is your workload read-heavy analytics on 100s GB to PB?
├─ YES → BigQuery
└─ NO → Is it relational with ACID transactions?
        ├─ YES → Is it production OLTP?
        │        ├─ YES → AlloyDB (modern) or Cloud SQL (legacy)
        │        └─ NO → AlloyDB (better features)
        └─ NO → Use NoSQL (Firestore, Datastore)
```

### Performance Comparison

```
Query: SELECT * FROM users WHERE signup_date > '2024-01-01'
(1 billion rows, need first 1000)

AlloyDB:
- Time: 50ms
- Why: Index on signup_date, return first 1000 only
- Cost: Per-instance pricing
- Good for: Real-time operations

BigQuery:
- Time: 5 seconds
- Why: Scans entire table (sorted by date)
- Cost: $0.0001 (data scanned)
- Good for: Full analysis, aggregations

Cloud SQL:
- Time: 100ms
- Why: Index on signup_date
- Cost: Per-instance pricing
- Good for: Legacy apps, small data
```

## When to Use AlloyDB

### Ideal Use Cases

#### 1. **High-Throughput OLTP Systems**
```sql
-- Example: Payment processing system
-- High write volume, real-time reads, transactions

CREATE TABLE transactions (
  transaction_id BIGSERIAL PRIMARY KEY,
  user_id BIGINT NOT NULL,
  amount DECIMAL(12, 2) NOT NULL,
  status VARCHAR(20) NOT NULL,
  created_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP
);

CREATE INDEX idx_user_created ON transactions(user_id, created_at);

-- AlloyDB handles:
-- - 10K+ writes/second
-- - <10ms latency
-- - Full ACID guarantees
-- - Automatic failover
```

#### 2. **Real-Time Analytics with Live Data**
```sql
-- Example: Research platform with live experiment data

CREATE TABLE experiment_results (
  experiment_id INT NOT NULL,
  run_id INT NOT NULL,
  timestamp TIMESTAMP NOT NULL,
  metric_name VARCHAR(100) NOT NULL,
  metric_value FLOAT NOT NULL,
  metadata JSONB,
  PRIMARY KEY (experiment_id, run_id, metric_name, timestamp)
);

-- AlloyDB:
-- - Researchers query live data
-- - Sub-second response
-- - Data immediately visible after insert
-- - JSONB for flexible experiment data
```

#### 3. **Master Data Management (MDM)**
```sql
-- Central source of truth for customer data

CREATE TABLE customers (
  customer_id BIGINT PRIMARY KEY,
  name VARCHAR(255) NOT NULL,
  email VARCHAR(255) NOT NULL UNIQUE,
  phone VARCHAR(20) NOT NULL,
  address JSONB,
  metadata JSONB,
  created_at TIMESTAMP NOT NULL,
  updated_at TIMESTAMP NOT NULL,
  version INT NOT NULL
);

-- AlloyDB handles:
-- - Real-time updates
-- - Cross-table consistency
-- - Complex transactions
-- - Multiple applications reading simultaneously
```

### When NOT to Use AlloyDB

```
❌ DON'T use AlloyDB for:

1. Petabyte-scale analytics
   → Use BigQuery instead

2. Immutable data warehouses
   → Use BigQuery (append-only model)

3. Unstructured data (images, videos)
   → Use Cloud Storage + BigQuery

4. No writes, only reads (reporting)
   → Use BigQuery (cheaper)

5. NoSQL use case
   → Use Firestore (document store)
```

## Integration Patterns

### Pattern 1: AlloyDB as Source, BigQuery as Analytics

```
Production Database (AlloyDB)
  ├─ Real-time transactional data
  ├─ High write volume
  └─ ACID compliance
         ↓ (Dataflow replication)
BigQuery Data Warehouse
  ├─ Historical analytics
  ├─ Read-only copies
  └─ Aggregated reporting
         ↓
BI Tools (Looker, Tableau)
  ├─ Dashboards
  ├─ Reports
  └─ Ad-hoc analysis
```

**Implementation (Dataflow):**

```python
from apache_beam import Pipeline, Create, ParDo
from apache_beam.io import WriteToText, WriteToBigQuery
from apache_beam.options.pipeline_options import PipelineOptions
import pg8000  # PostgreSQL driver

class ReadFromAlloyDB(beam.DoFn):
    def process(self, element):
        # Connect to AlloyDB
        conn = pg8000.connect(
            host='alloydb-instance-ip',
            user='app_user',
            password='password',
            database='production'
        )
        
        # Read changed data (CDC - Change Data Capture)
        cursor = conn.cursor()
        cursor.execute("""
            SELECT customer_id, name, email, updated_at
            FROM customers
            WHERE updated_at > NOW() - INTERVAL '1 hour'
        """)
        
        for row in cursor.fetchall():
            yield {
                'customer_id': row[0],
                'name': row[1],
                'email': row[2],
                'updated_at': row[3],
                'processed_at': datetime.now()
            }
        
        conn.close()

pipeline = Pipeline(options=PipelineOptions())
(pipeline 
 | 'Read from AlloyDB' >> beam.ParDo(ReadFromAlloyDB())
 | 'Write to BigQuery' >> WriteToBigQuery(
     dataset='analytics_prod',
     table='customers',
     schema='customer_id:INTEGER, name:STRING, email:STRING, updated_at:TIMESTAMP, processed_at:TIMESTAMP'
 )
)

pipeline.run()
```

### Pattern 2: AlloyDB + BigQuery Materialized View

```sql
-- In AlloyDB: Source data
SELECT 
  customer_id,
  COUNT(*) as order_count,
  SUM(amount) as total_spent,
  MAX(order_date) as last_order_date
FROM orders
GROUP BY customer_id;

-- Replicate to BigQuery
-- Create materialized view on top

CREATE MATERIALIZED VIEW IF NOT EXISTS analytics_prod.mv_customer_metrics AS
SELECT 
  c.customer_id,
  c.name,
  co.order_count,
  co.total_spent,
  co.last_order_date,
  ROUND(co.total_spent / NULLIF(co.order_count, 0), 2) as avg_order_value
FROM `my-project.analytics_prod.customers` c
LEFT JOIN `my-project.analytics_prod.customer_orders` co
  ON c.customer_id = co.customer_id;

-- Queries hitting MV are instant
SELECT * FROM mv_customer_metrics
WHERE total_spent > 10000
ORDER BY avg_order_value DESC;
```

## Performance Characteristics

### Typical AlloyDB Performance

```
Single Query:
└─ Complex JOIN on 100M rows: 200-500ms
└─ Aggregation on 1B rows: 2-5 seconds
└─ Point lookup (indexed): <10ms

Throughput:
└─ OLTP: 10,000+ QPS (queries per second)
└─ Read replicas: Linear scaling with replicas
└─ Writes: Limited by primary instance

Latency:
└─ Read latency from replica: <10ms (same region)
└─ Write latency: 5-20ms (replication lag)
└─ Cross-region replica: 100-500ms (network dependent)
```

### Scaling Strategies

```sql
-- Strategy 1: Vertical Scaling (larger instance)
-- Limitations: Single machine bottleneck (network, CPU)
-- Suitable for: <100K QPS

-- Strategy 2: Horizontal Read Scaling
-- Add read replicas in different regions
-- Unlimited scaling for reads
-- Suitable for: 100K+ QPS read-heavy

-- Strategy 3: Sharding
-- Split data by customer/region/tenant
-- Each shard is smaller AlloyDB instance
-- Suitable for: Multi-tenant (Accenture research)

-- Example sharding for research:
SELECT customer_hash(project_id) % num_shards as shard_id
FROM research_projects;

-- Direct to appropriate shard for reads/writes
```

```sql
-- AlloyDB Schema for Accenture Research

-- Projects table
CREATE TABLE research_projects (
  project_id BIGSERIAL PRIMARY KEY,
  project_name VARCHAR(255) NOT NULL,
  description TEXT,
  principal_investigator_id BIGINT NOT NULL,
  team_id BIGINT NOT NULL,
  status VARCHAR(20) NOT NULL,
  created_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
  updated_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP
);

-- Experiments table
CREATE TABLE experiments (
  experiment_id BIGSERIAL PRIMARY KEY,
  project_id BIGINT NOT NULL REFERENCES research_projects(project_id),
  experiment_name VARCHAR(255) NOT NULL,
  description TEXT,
  hypothesis TEXT,
  methodology JSONB,
  status VARCHAR(20) NOT NULL,
  start_date TIMESTAMP NOT NULL,
  end_date TIMESTAMP,
  created_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP
);

-- Real-time experiment results
CREATE TABLE experiment_results (
  result_id BIGSERIAL PRIMARY KEY,
  experiment_id BIGINT NOT NULL REFERENCES experiments(experiment_id),
  metric_name VARCHAR(100) NOT NULL,
  metric_value FLOAT NOT NULL,
  timestamp TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
  metadata JSONB,
  measurement_method VARCHAR(100) NOT NULL
);

-- Create indexes for fast queries
CREATE INDEX idx_exp_project ON experiments(project_id);
CREATE INDEX idx_results_exp_time ON experiment_results(experiment_id, timestamp);
CREATE INDEX idx_results_metric ON experiment_results(metric_name, timestamp);

-- Real-time aggregation (materialized view)
CREATE MATERIALIZED VIEW experiment_summary AS
SELECT 
  experiment_id,
  COUNT(*) as total_measurements,
  COUNT(DISTINCT metric_name) as unique_metrics,
  MIN(timestamp) as first_measurement,
  MAX(timestamp) as latest_measurement
FROM experiment_results
GROUP BY experiment_id;
```

**Benefits for Research:**

- Complex transactions (experiment state changes)
- Point-in-time queries (what was status at X time?)
- Audit trail (all changes logged)

## Interview Questions

### Q1: "We have OLTP production + need analytics. Recommend architecture?"

**Answer:**
1. **Production data**: AlloyDB (real-time, ACID, high throughput)
2. **Analytics data**: BigQuery (historical, aggregated, unlimited scale)
3. **Integration**: Dataflow replication (hourly/daily sync)
4. **Trade-off**: Small latency (data sync delay) for massive analytics scale

### Q2: "When would you choose AlloyDB over BigQuery?"

**Answer:**
- Real-time transactions (OLTP)
- Need writes/updates (not append-only)
- Strict ACID requirements
- Sub-second latency critical
- Complex relationships (JOINs, foreign keys)

**When to choose BigQuery:**
- Analytics (read-heavy)
- Petabyte scale
- Append-only data
- Aggregations
- Cost-sensitive (pay per query, not instance)

### Q3: "Design database for research platform with 60+ projects."

**Answer:**
- **AlloyDB primary**: Project metadata, experiment config, real-time results
- **AlloyDB read replicas**: Distributed globally for low latency
- **BigQuery**: Historical analysis, cross-experiment insights
- **Sync**: Dataflow pipeline (hourly)
- **Benefits**: Fast writes, real-time, scalable reads, unlimited analytics
