## Data Governance Fundamentals

### What is Data Governance?

**Data Governance** = Organizational structure and policies managing data assets

```
Data Governance Components:

┌────────────────────────────────────────────┐
│         ORGANIZATIONAL STRUCTURE            │
├────────────────────────────────────────────┤
│ • Chief Data Officer (CDO)                 │
│ • Data Governance Board                    │
│ • Data Stewards (per domain)               │

        ↓
```

### Key Roles & Responsibilities

| Role | Responsibility | Authority |
|------|-----------------|-----------|
| **Data Owner** | Decide who accesses their data | Approve/deny access requests |
| **Data Steward** | Maintain data quality standards | Enforce naming conventions, document |
| **Data Custodian** | Technical implementation | Configure IAM, encryption, backups |
| **DPO** | Privacy compliance | GDPR, data deletion, consent mgmt |
| **Security Officer** | Data security | Encryption, vulnerability assessment |

## Metadata Management

### What is Metadata?

**Metadata** = Data about data

```
Metadata Types:

1. TECHNICAL METADATA
   - Schema (columns, types, constraints)
   - Table size, row count
   - Partitioning/clustering strategy
   - Refresh frequency
   - Storage location

2. BUSINESS METADATA
   - Business glossary terms
   - Data ownership
   - Use cases
   - Calculation logic
   - Stakeholders

3. OPERATIONAL METADATA
   - Last run time
   - Data freshness
   - Error logs
   - SLAs, quality scores
   - Change history
```

### Lineage Queries

```sql
-- Find all upstream dependencies (what feeds into this table?)
WITH RECURSIVE upstream AS (
  -- Base case: target table
  SELECT
    target_table,
    source_table,
    1 as hop_level
  FROM `my_project.governance.data_lineage`
  WHERE target_table = 'analytics_prod.fact_sales'
  
  UNION ALL
  
  -- Recursive case: find upstream of sources
  SELECT
    up.target_table,
    dl.source_table,
    up.hop_level + 1
  FROM upstream up
  JOIN `my_project.governance.data_lineage` dl
    ON up.source_table = dl.target_table
  WHERE up.hop_level < 10  -- Prevent infinite loops
)
SELECT DISTINCT
  source_table,
  hop_level,
  MAX(hop_level) OVER () as max_hops
FROM upstream
ORDER BY hop_level;

-- Find all downstream dependencies (what depends on this table?)
WITH RECURSIVE downstream AS (
  SELECT
    source_table,
    target_table,
    1 as hop_level
  FROM `my_project.governance.data_lineage`
  WHERE source_table = 'raw_prod.transactions'
  
  UNION ALL
  
  SELECT
    down.source_table,
    dl.target_table,
    down.hop_level + 1
  FROM downstream down
  JOIN `my_project.governance.data_lineage` dl
    ON down.target_table = dl.source_table
  WHERE down.hop_level < 10
)
SELECT DISTINCT
  target_table,
  hop_level
FROM downstream
ORDER BY hop_level;

-- Impact analysis: Which reports affected if table fails?
SELECT
  target_table,
  (SELECT COUNT(*) FROM `my_project.governance.dashboard_dependencies`
   WHERE dashboard_table = dl.target_table) as num_dashboards_affected
FROM `my_project.governance.data_lineage` dl
WHERE source_table = 'production.critical_table'
ORDER BY num_dashboards_affected DESC;
```

```python
class DataProcessingAgreement:
    """Track GDPR compliance requirements"""
    
    def __init__(self, data_processor: str, data_controller: str):
        self.processor = data_processor
        self.controller = data_controller
        self.processing_purposes = []  # Why is data processed?
        self.legal_basis = None  # Consent? Legitimate interest?
        self.retention_period = None  # How long keep?
        self.subject_rights = []  # Right to delete, access, etc.
    
    def add_processing_purpose(self, purpose: str, retention_days: int):
        """Add processing purpose with retention"""
        self.processing_purposes.append({
            'purpose': purpose,
            'retention_days': retention_days,
            'deletion_scheduled': self.get_deletion_date(retention_days)
        })

# 2. Right to be forgotten (RTBF) implementation
def delete_user_data(user_id: str):
    """Implement GDPR right to deletion"""
    
    client = bigquery.Client()
    
    # Step 1: Find all tables containing user_id
    query = """
    SELECT table_schema, table_name
    FROM `my_project.analytics_prod.INFORMATION_SCHEMA.COLUMNS`
    WHERE column_name = 'user_id'
    """
    
    tables = client.query(query).result()
    
    # Step 2: Delete user records from all tables
    for table in tables:
        delete_query = f"""
        DELETE FROM `{table['table_schema']}.{table['table_name']}`
        WHERE user_id = '{user_id}'
        """
        client.query(delete_query).result()
    
    # Step 3: Log deletion for audit trail
    log_entry = {
        'user_id': user_id,
        'deletion_timestamp': datetime.now(),
        'tables_affected': len(list(tables))
    }
    
    print(f"User {user_id} deleted from {len(list(tables))} tables")

# 3. Privacy by Design: Pseudonymization
def pseudonymize_pii(email: str) -> str:
    """Hash PII to prevent identification"""
    import hashlib
    
    # Hash with salt
    salt = "company_specific_salt"
    return hashlib.sha256(f"{email}{salt}".encode()).hexdigest()[:16]

# 4. Data Protection Impact Assessment (DPIA)
class DPIA:
    """Document processing activities & risks"""
    
    def __init__(self, processing_activity: str):
        self.activity = processing_activity
        self.personal_data_types = []
        self.data_subjects = []
        self.risks = []
        self.mitigations = []
    
    def add_risk(self, risk: str, severity: str, mitigation: str):
        """Document risk & how to mitigate"""
        self.risks.append({
            'risk': risk,
            'severity': severity,  # low, medium, high
            'mitigation': mitigation
        })
```

## Privacy & Security

### Data Masking Strategies

```sql
-- Sensitive data masking in queries

-- 1. Hash sensitive columns
SELECT
    customer_id,
    SHA256(CONCAT(email, 'salt')) as email_hash,  -- One-way hash
    SHA256(phone) as phone_hash,
    amount
FROM customers;

-- 2. Tokenization: Replace with token
SELECT
    SUBSTR(credit_card_number, 1, 4) || 'XXXX-XXXX-XXXX-' || 
    SUBSTR(credit_card_number, -4) as masked_cc,  -- 4111-XXXX-XXXX-1111
    amount
FROM transactions;

-- 3. Redaction: NULL out sensitive columns
SELECT
    CASE WHEN CURRENT_USER() LIKE '%@company.com' 
         THEN ssn 
         ELSE NULL 
    END as ssn,  -- Only company employees see SSN
    amount
FROM employees;

-- 4. Aggregation: Hide individual records
SELECT
    DATE_TRUNC(birth_date, YEAR) as birth_year,  -- Year only
    SUBSTR(zip_code, 1, 3) || '00' as zip_area,   -- Area code only
    COUNT(*) as count
FROM customers
GROUP BY birth_year, zip_area;
```

### Access Control Implementation

```sql
-- Row-level security (RLS) in BigQuery

-- 1. User-based filtering
CREATE OR REPLACE VIEW vw_customer_data_secure AS
SELECT *
FROM customers
WHERE department = (
  SELECT department FROM employees WHERE email = SESSION_USER()
);
-- User can only see customers in their department

-- 2. Column-level security
CREATE OR REPLACE VIEW vw_customer_data_masked AS
SELECT
    customer_id,
    CASE WHEN HAS_ROLE('analyst') THEN email ELSE NULL END as email,
    CASE WHEN HAS_ROLE('analyst') THEN phone ELSE NULL END as phone,
    CASE WHEN HAS_ROLE('finance') THEN salary ELSE NULL END as salary,
    amount
FROM customers;
-- Analysts see email/phone, Finance sees salary, others see nothing

-- 3. Dynamic masking based on role
CREATE OR REPLACE FUNCTION mask_pii(value STRING, role STRING)
RETURNS STRING
LANGUAGE SQL
AS (
  CASE 
    WHEN role = 'admin' THEN value
    WHEN role = 'analyst' THEN CONCAT(SUBSTR(value, 1, 2), 'XXXX')
    ELSE 'REDACTED'
  END
);

SELECT
    customer_id,
    mask_pii(email, CURRENT_ROLE()) as email,
    mask_pii(ssn, CURRENT_ROLE()) as ssn
FROM customers;
```

## Interview Questions

### Q1: "Design governance framework for research platform with 60+ projects."

**Answer**:
1. **Metadata catalog**: Track all datasets, ownership, classification
2. **Access control**: Project isolation, role-based access
3. **Quality framework**: Automated validation per project
4. **Lineage tracking**: dbt manages transformations
5. **Compliance**: GDPR/CCPA controls via masking/RLS
6. **Audit**: All access logged, monthly reviews

### Q2: "How to comply with GDPR right-to-delete?"

**Answer**:
1. **Identify**: Find all records for user
2. **Delete**: Remove from all systems (operational + analytics)
3. **Verify**: Confirm deletion via audit query
4. **Log**: Document deletion for audit trail
5. **Communicate**: Confirm to user within 30 days
6. **Monitor**: Alerts if data reappears

### Q3: "Data governance for 100+ sources. How to scale?"

**Answer**:
1. **Metadata as code**: Define governance in dbt YAML
2. **Automated discovery**: Scan new tables, apply default tags
3. **Self-service catalog**: Enable teams to document their data
4. **Exception framework**: Define why data violates standards
5. **Monitoring**: Dashboard of governance metrics
6. **Incentives**: Reward teams with high governance scores
