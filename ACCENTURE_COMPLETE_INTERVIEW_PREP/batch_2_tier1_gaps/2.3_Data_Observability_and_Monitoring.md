## Data Observability Concepts

### What is Data Observability?

**Data Observability** = Ability to understand and trace data health across systems

```
vs.

Traditional Monitoring (System Monitoring):
├─ CPU usage: 75%
├─ Memory: 6 GB / 8 GB
├─ Disk: 500 GB available
└─ Network latency: 5ms

Data Observability (Data-Centric):
├─ Data freshness: 3 hours old (SLA: <24 hours)
├─ Completeness: 95% of expected rows
├─ Anomalies: 2 outliers detected
└─ Lineage impact: Affects 12 downstream dashboards
```

### Four Pillars of Data Observability

```
┌──────────────────────────────────────┐
│   FOUR PILLARS OF OBSERVABILITY      │
├──────────────────────────────────────┤
│                                      │
│ 1. FRESHNESS                         │
│    How recent is data?               │
│    - Last update time                │
│    - Time since last successful load │
│    - SLA: <24 hours for daily data   │
│                                      │
│ 2. DISTRIBUTION (Anomalies)          │
│    Are values within normal range?   │
│    - Statistical anomaly detection   │
│    - Null rate spikes                │
│    - Out-of-range values             │
│                                      │
│ 3. SCHEMA                            │
│    Is structure as expected?         │
│    - Column presence                 │
│    - Type mismatches                 │
│    - Unexpected new columns          │
│                                      │
│ 4. LINEAGE                           │
│    What depends on this data?        │
│    - Upstream dependencies           │
│    - Downstream impact               │
│    - Blast radius of failures        │
│                                      │
└──────────────────────────────────────┘
```

### Observability vs. Monitoring

| Aspect | Monitoring | Observability |
|--------|-----------|---|
| **Questions Answered** | Is system working? | Why is system broken? |
| **Data Required** | Metrics, logs | Metrics, logs, traces, lineage |
| **Approach** | Reactive alerts | Proactive understanding |
| **Tools** | Prometheus, Grafana | Databand, Monte Carlo, Great Expectations |
| **Benefit** | Uptime SLA | Data quality SLA |

## Key Metrics & KPIs

### Freshness Metrics

```sql
-- Track data freshness over time
CREATE OR REPLACE VIEW monitoring.vw_data_freshness AS

WITH latest_updates AS (
  SELECT
    'events' as table_name,
    MAX(processed_timestamp) as last_update_time,
    TIMESTAMP_DIFF(CURRENT_TIMESTAMP(), MAX(processed_timestamp), HOUR) as hours_stale
  FROM raw_prod.events
  WHERE processed_timestamp >= TIMESTAMP_SUB(CURRENT_TIMESTAMP(), INTERVAL 7 DAY)
  
  UNION ALL
  
  SELECT
    'users',
    MAX(updated_at),
    TIMESTAMP_DIFF(CURRENT_TIMESTAMP(), MAX(updated_at), HOUR)
  FROM analytics_prod.users
  
  UNION ALL
  
  SELECT
    'orders',
    MAX(created_at),
    TIMESTAMP_DIFF(CURRENT_TIMESTAMP(), MAX(created_at), HOUR)
  FROM analytics_prod.orders
)

SELECT
  table_name,
  last_update_time,
  hours_stale,
  CASE 
    WHEN hours_stale = 0 THEN 'Fresh (< 1 hour)'
    WHEN hours_stale <= 1 THEN 'Recent (< 2 hours)'
    WHEN hours_stale <= 24 THEN 'Acceptable (< 1 day)'
    WHEN hours_stale <= 48 THEN 'Stale (1-2 days)'
    ELSE 'Very Stale (> 2 days)'
  END as freshness_status,
  CASE
    WHEN hours_stale <= 24 THEN 1  -- Passing SLA
    WHEN hours_stale <= 48 THEN 0.5  -- Warning
    ELSE 0  -- Failed
  END as sla_score
FROM latest_updates
ORDER BY hours_stale DESC;
```

### Volume & Completeness Metrics

```sql
-- Track data volume anomalies
CREATE OR REPLACE VIEW monitoring.vw_data_volume AS

WITH daily_counts AS (
  SELECT
    DATE(processed_timestamp) as event_date,
    COUNT(*) as event_count,
    COUNT(DISTINCT user_id) as unique_users,
    AVG(TIMESTAMP_DIFF(processed_timestamp, event_timestamp, SECOND)) as avg_latency_seconds
  FROM raw_prod.events
  WHERE processed_timestamp >= TIMESTAMP_SUB(CURRENT_DATE(), INTERVAL 30 DAY)
  GROUP BY event_date
),

stats AS (
  SELECT
    APPROX_QUANTILES(event_count, 100)[OFFSET(25)] as q25_events,
    APPROX_QUANTILES(event_count, 100)[OFFSET(50)] as q50_events,
    APPROX_QUANTILES(event_count, 100)[OFFSET(75)] as q75_events,
    APPROX_QUANTILES(event_count, 100)[OFFSET(5)] as p5_events,
    APPROX_QUANTILES(event_count, 100)[OFFSET(95)] as p95_events
  FROM daily_counts
)

SELECT
  dc.event_date,
  dc.event_count,
  dc.unique_users,
  dc.avg_latency_seconds,
  CASE
    WHEN dc.event_count < s.p5_events THEN 'ANOMALY_LOW'
    WHEN dc.event_count > s.p95_events THEN 'ANOMALY_HIGH'
    WHEN dc.event_count < s.q25_events THEN 'WARNING_LOW'
    WHEN dc.event_count > s.q75_events THEN 'WARNING_HIGH'
    ELSE 'NORMAL'
  END as volume_status,
  s.p5_events,
  s.p95_events
FROM daily_counts dc
CROSS JOIN stats s
ORDER BY event_date DESC;
```

### Data Quality Metrics

```sql
-- Comprehensive data quality scorecard
CREATE OR REPLACE VIEW monitoring.vw_quality_scorecard AS

WITH quality_scores AS (
  SELECT
    DATE(processed_timestamp) as quality_date,
    
    -- Completeness: % records with all required fields
    ROUND(
      COUNTIF(event_id IS NOT NULL AND user_id IS NOT NULL AND event_type IS NOT NULL) 
      / COUNT(*),
      4
    ) as completeness_score,
    
    -- Uniqueness: % unique event_ids
    ROUND(
      COUNT(DISTINCT event_id) / COUNT(*),
      4
    ) as uniqueness_score,
    
    -- Validity: % events with valid types
    ROUND(
      COUNTIF(event_type IN ('click', 'view', 'purchase', 'scroll'))
      / COUNT(*),
      4
    ) as validity_score,
    
    -- Timeliness: % events processed within SLA
    ROUND(
      COUNTIF(TIMESTAMP_DIFF(processed_timestamp, event_timestamp, MINUTE) < 60)
      / COUNT(*),
      4
    ) as timeliness_score,
    
    -- Accuracy: % events with valid timestamps
    ROUND(
      COUNTIF(event_timestamp <= processed_timestamp)
      / COUNT(*),
      4
    ) as accuracy_score
    
  FROM raw_prod.events
  WHERE processed_timestamp >= TIMESTAMP_SUB(CURRENT_DATE(), INTERVAL 30 DAY)
  GROUP BY quality_date
)

SELECT
  quality_date,
  ROUND((completeness_score + uniqueness_score + validity_score + 
         timeliness_score + accuracy_score) / 5, 4) as overall_quality_score,
  completeness_score,
  uniqueness_score,
  validity_score,
  timeliness_score,
  accuracy_score,
  CASE
    WHEN (completeness_score + uniqueness_score + validity_score + 
          timeliness_score + accuracy_score) / 5 >= 0.99 THEN 'EXCELLENT'
    WHEN (completeness_score + uniqueness_score + validity_score + 
          timeliness_score + accuracy_score) / 5 >= 0.95 THEN 'GOOD'
    WHEN (completeness_score + uniqueness_score + validity_score + 
          timeliness_score + accuracy_score) / 5 >= 0.90 THEN 'ACCEPTABLE'
    ELSE 'POOR'
  END as quality_grade
FROM quality_scores
ORDER BY quality_date DESC;
```

### Pipeline Health Metrics

```python
# Track Airflow DAG health
from airflow.models import DagRun, TaskInstance
from datetime import datetime, timedelta

def get_dag_health_metrics():
    """Get DAG execution metrics"""
    
    metrics = {
        'total_dags': 0,
        'healthy_dags': 0,
        'failed_dags': 0,
        'avg_duration_minutes': 0,
        'average_success_rate': 0
    }
    
    # Get recent dag runs (last 7 days)
    dag_runs = DagRun.filter(
        DagRun.execution_date >= datetime.now() - timedelta(days=7)
    )
    
    total_runs = 0
    successful_runs = 0
    total_duration = 0
    
    for dag_run in dag_runs:
        total_runs += 1
        
        if dag_run.state == 'success':
            successful_runs += 1
        
        if dag_run.end_date and dag_run.start_date:
            duration = (dag_run.end_date - dag_run.start_date).total_seconds() / 60
            total_duration += duration
    
    metrics['total_dags'] = total_runs
    metrics['failed_dags'] = total_runs - successful_runs
    metrics['healthy_dags'] = successful_runs
    metrics['average_success_rate'] = successful_runs / total_runs if total_runs > 0 else 0
    metrics['avg_duration_minutes'] = total_duration / total_runs if total_runs > 0 else 0
    
    return metrics

# Output metrics to Cloud Monitoring
from google.cloud import monitoring_v3

def publish_metrics(metrics: dict):
    """Publish metrics to Cloud Monitoring"""
    
    client = monitoring_v3.MetricServiceClient()
    project_name = client.project_path('my-project')
    
    for metric_name, metric_value in metrics.items():
        series = monitoring_v3.TimeSeries()
        series.metric.type_ = f'custom.googleapis.com/airflow/{metric_name}'
        
        now = time.time()
        seconds = int(now)
        nanos = int((now - seconds) * 10 ** 9)
        interval = monitoring_v3.TimeInterval(
            {"seconds": seconds, "nanos": nanos}
        )
        point = monitoring_v3.Point(
            {"interval": interval, "value": {"double_value": metric_value}}
        )
        series.points = [point]
        
        client.create_time_series(name=project_name, time_series=[series])
```

```yaml
    severity: high
    notification_channels:
      - slack: #data-quality
    runbook: https://wiki.company.com/data-quality-degradation
  
  - name: volume_anomaly
    description: Daily event count is statistical anomaly
    condition: |
      SELECT event_date, event_count, volume_status
      FROM monitoring.vw_data_volume
      WHERE volume_status IN ('ANOMALY_LOW', 'ANOMALY_HIGH')
    severity: medium
    notification_channels:
      - slack: #data-alerts
    context: |
      Expected range: {p5_events} - {p95_events}
      Actual: {event_count}
  
  - name: pipeline_failure_rate
    description: DAG failure rate above threshold
    condition: |
      WITH recent_runs AS (
        SELECT 
          dag_id,
          COUNT(*) as total_runs,
          SUM(CASE WHEN state = 'failed' THEN 1 ELSE 0 END) as failed_runs
        FROM airflow_metrics.dag_runs
        WHERE execution_date >= CURRENT_TIMESTAMP() - INTERVAL 24 HOUR
        GROUP BY dag_id
      )
      SELECT dag_id, 
             ROUND(failed_runs / total_runs, 4) as failure_rate
      FROM recent_runs
      WHERE failed_runs / total_runs > 0.05  -- >5% failure rate
    severity: critical
    notification_channels:
      - pagerduty: infra-oncall
      - slack: #critical-alerts
```

### Incident Response Playbook

```yaml
incident_response:
  data_freshness_failure:
    description: Data in analytics layer is stale
    severity: high
    steps:
      1. confirm_issue: |
         - Check last successful pipeline run
         - Verify no manual updates
         - Confirm with stakeholders impact
      
      2. root_cause_analysis: |
         - Check ingestion logs for errors
         - Verify source system availability
         - Check for schema changes
         - Review recent code changes (dbt, airflow)
      
      3. immediate_action: |
         - If ingestion failure: retry pipeline
         - If source down: wait for source recovery
         - If quota exceeded: request increase
         - If schema broken: rollback changes
      
      4. notification: |
         - Update stakeholders on status
         - Share ETA for resolution
         - Post to #data-incidents Slack channel
      
      5. resolution: |
         - Fix root cause
         - Re-run pipeline
         - Verify data freshness
         - Confirm downstream dashboards updated
      
      6. post_mortem: |
         - Document what happened
         - Identify preventive measures
         - Create tracking issue for improvements
         - Schedule 30-day follow-up

  data_quality_regression:
    steps:
      1. determine_scope: |
         - Which tables/columns affected?
         - When did regression start?
         - How many records affected?
      
      2. assess_impact: |
         - Which reports/models use this data?
         - How many users affected?
         - What decisions rely on this data?
      
      3. quarantine: |
         - Mark affected data as unreliable
         - Add warning to dashboards
         - Create alternate (clean) data source if possible
      
      4. remediation: |
         - Fix data quality issue
         - Re-process affected records
         - Revalidate quality checks
      
      5. communication: |
         - Notify data consumers
         - Explain impact & mitigation
         - Update documentation
```

### Incident Response Metrics

```python
# Track incident response quality
from datetime import datetime

class IncidentMetrics:
    """Measure incident response performance"""
    
    def __init__(self, incident_id: str):
        self.incident_id = incident_id
        self.created_time = datetime.now()
        self.detected_time = None
        self.alert_time = None
        self.ack_time = None
        self.resolved_time = None
    
    @property
    def detection_lag(self):
        """Time from issue to detection"""
        return (self.detected_time - self.created_time).total_seconds()
    
    @property
    def mean_time_to_alert(self, mtta):
        """Time from detection to alerting"""
        return (self.alert_time - self.detected_time).total_seconds()
    
    @property
    def mean_time_to_acknowledge(self, mttr):
        """Time from alert to acknowledgment"""
        return (self.ack_time - self.alert_time).total_seconds()
    
    @property
    def mean_time_to_resolve(self, mttr):
        """Time from issue to resolution"""
        return (self.resolved_time - self.created_time).total_seconds()
    
    def __str__(self):
        return f"""
        Incident {self.incident_id}
        ─────────────────────
        Detection Lag: {self.detection_lag / 60:.1f} min
        MTTA: {self.mean_time_to_alert / 60:.1f} min
        MTTR: {self.mean_time_to_resolve / 60:.1f} min
        """
```

## Interview Questions

### Q1: "How to detect data quality issues in real-time?"

**Answer**:
1. **Statistical baselines**: Learn normal patterns from historical data
2. **Automated validation**: dbt tests on every run
3. **Anomaly detection**: Z-score, IQR for outliers
4. **Freshness monitoring**: Track last update time
5. **Volume monitoring**: Alert on drastic row count changes
6. **Lineage tracking**: Know downstream impact immediately
7. **Smart alerting**: ML-based to reduce false positives

### Q2: "Dashboard shows wrong numbers. Root cause in 5 minutes?"

**Answer**:
1. **Lineage view**: See all upstream dependencies
2. **Last successful run**: When did data last update?
3. **Execution logs**: Any errors in pipeline?
4. **Quality metrics**: Did quality check fail?
5. **Source reconciliation**: Does source data match warehouse?
6. **Recent changes**: Was DAG/query modified?
7. **Quick fix**: Either rerun pipeline or show cached data

### Q3: "Design observability for 50+ data pipelines."

**Answer**:
1. **Unified metrics**: BigQuery table for all pipeline metrics
2. **Standard KPIs**: Freshness, volume, quality, latency
3. **Automated discovery**: Scan pipelines, apply monitoring
4. **Dashboard per team**: View their pipeline health
5. **Centralized alerts**: Route to correct team/oncall
6. **Playbooks**: Runbooks for common issues
7. **Metrics: target SLAs (99.5% uptime, <1hr latency, >95% quality)
